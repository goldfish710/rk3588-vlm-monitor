## 1. 系统总体架构

```
RK3568 板端 (TLServer)                          PC 端 (LLClient)
┌─────────────────────────────────────┐         ┌────────────────────┐
│ IMX335 MIPI 摄像头                  │         │ QT6 界面           │
│   ├─ ISP mainpath → /dev/video0     │         │ FFmpeg RTSP 拉流   │
│   │   2592x1944 → H.265 → RTSP /h265│◄───────►│ NVIDIA cuvid 硬解  │
│   └─ ISP selfpath → /dev/video1     │  RTSP   │ 主/子码流切换      │
│       640x480 → AI推理+绘图 → H.264 │  8554   │ 截图 / 录像        │
│              → RTSP /h264           │         └────────────────────┘
│                                    │
│ AI: RKNN NPU 推理 yolov8n-pose     │
│   → 跌倒/坐姿分类 → 多人追踪        │
│   → 事件: 存图 + SQLite + MQTT     │
│ 录像: 循环录像 + 跌倒事件切片       │
└─────────────────────────────────────┘
```

**为什么用双码流？** 主码流高清（2592x1944）用于人看和录像，子码流低清（640x480）用于 AI 推理——AI 不需要高清，分辨率越低 NPU 推理越快。两者由摄像头 ISP 硬件同时输出，互不干扰。

## 2. 视频采集：V4L2 MPLANE + DMABUF 零拷贝

### 2.1 什么是 V4L2
Video4Linux2，Linux 内核的视频设备驱动标准接口。用户空间通过 `open()` + `ioctl()` 操作 `/dev/videoX` 完成：查询能力 → 设置格式 → 申请缓冲 → 入队/出队 → 开关流。

### 2.2 标准 V4L2 采集流程（本项目实际流程）
1. `open("/dev/video0")` 打开设备
2. `VIDIOC_QUERYCAP` 查询能力，确认支持 `V4L2_CAP_VIDEO_CAPTURE_MPLANE`（多平面采集）
3. `VIDIOC_S_FMT` 设置格式：**MPLANE（多平面）**，NV12（YUV420SP），2592x1944
4. `VIDIOC_REQBUFS` 申请缓冲，内存类型用 **V4L2_MEMORY_DMABUF** —— 关键点！
5. `VIDIOC_QBUF` 把缓冲入队给驱动
6. `VIDIOC_STREAMON` 开始采集
7. 循环 `VIDIOC_DQBUF`（取出装满的帧）→ 处理 → `VIDIOC_QBUF`（还给驱动）

### 2.3 MPLANE（多平面）是什么
NV12 格式分两个平面：Y 亮度平面 + 交错的 UV 色度平面。普通（单平面）V4L2 把两个平面拼在一段连续内存里；**MPLANE 允许每个平面放在不同内存地址**。硬件编解码器（MPP）的 DMA 输入往往要求平面分开，MPLANE 可以免去一次拷贝。

### 2.4 DMABUF 零拷贝（本项目核心优化点）
传统流程：`mmap` 映射驱动内存 → 用户态读帧 → `memcpy` 拷到编码器缓冲 → 编码。内存拷贝是性能杀手（2592x1944 NV12 一帧约 7.5MB，30fps 每秒 225MB 的拷贝量）。

DMABUF 方案：
1. **MPP 编码器先分配**自己的输入缓冲（`mpp_buffer_get_fd` 拿到 dma-buf 文件描述符 fd）
2. 把 MPP 的 fd **导入 V4L2**（`V4L2_MEMORY_DMABUF` + `m.fd = fd`）
3. V4L2 驱动直接 DMA 写入 MPP 的内存；MPP 直接 DMA 读出编码
4. **全程零 CPU 拷贝**，数据只经 DMA 总线流动

```
摄像头 ISP ──DMA──► MPP 分配的 dma-buf ──DMA──► MPP 编码器 ──► 码流
                         ▲
                   V4L2 驱动直接写入
                   （fd 在两者间共享）
```

**面试要点**：零拷贝 = 不经过 CPU 内存拷贝，通过内核 dma-buf 机制在不同硬件模块间共享同一块物理内存。同理，RKNN 的 `rknn_create_mem` 零拷贝 API 也是这个思想。

## 3. 硬件编码：RK MPP

### 3.1 什么是 MPP
Media Process Platform，Rockchip 的媒体处理库，封装了芯片内置的硬件视频编解码器（VPU）。API 风格类似 ffmpeg 的底层接口：`MppCtx`（编码器上下文）、`MppApi`（函数指针表）、`MppPacket`（码流包）、`MppFrame`（原始帧）、`MppBuffer`（dma 缓冲）。

### 3.2 编码流程
```
encode_put_frame(ctx, frame)   // 送入一帧 YUV
encode_get_packet(ctx, &pkt)   // 取出编码好的码流（H.265/H.264）
```

### 3.3 关键编码参数（本项目配置）
| 参数 | 主码流 | 子码流 | 含义 |
|---|---|---|---|
| 编码格式 | H.265 (HEVC) | H.264 (AVC) | H.265 压缩率比 H.264 高约 50%，同画质码率减半，但解码耗资源 |
| 码率控制 | 4Mbps CBR | 1.5Mbps CBR | **CBR 恒定码率**：网络传输稳；对比 VBR 可变码率：质量稳。监控场景选 CBR |
| GOP | 30 | 15 | **GOP（Group of Pictures）**：两个 I 帧之间的间隔。I 帧 = 关键帧（完整画面），P 帧 = 只含差异。GOP=30 即每 30 帧（1 秒）一个 I 帧 |
| stride | 2592/1952 | 640/480 | **对齐步长**：硬件要求宽高按 16 字节对齐，实际存储行宽 ≥ 显示宽 |

### 3.4 IDR 帧与录像切片
- **I 帧/IDR 帧**：可以独立解码的完整帧。解码器必须从 IDR 帧开始才能解出画面（P 帧依赖前面的帧）
- 录像切片时**必须从 IDR 帧开始写文件**，否则切片视频前几帧花屏
- 本项目：GOP 主码流 1 秒、子码流 0.5 秒，保证事件录像起点对齐误差小
- MPP 通过 `mpp_packet_get_flag()` 判断包是否为 IDR（bit0 标志）

### 3.5 VPS / SPS / PPS 参数集
H.265 码流中的"全局配置信息"：
- **VPS**（视频参数集）：H.265 独有，描述码流总体结构
- **SPS**（序列参数集）：分辨率、帧率、profile 等级
- **PPS**（图像参数集）：熵编码模式、量化参数

播放器/录像文件开头必须有参数集才能解码。MPP 编码时会周期性输出，但**每个切片文件必须自己在文件头注入一份**（见第 11 章）。

## 4. 流媒体传输：RTSP / RTP / live555

### 4.1 协议栈
```
RTSP  : 控制协议（文本协议，类似 HTTP）—— PLAY / PAUSE / TEARDOWN / DESCRIBE
RTP   : 实时传输协议 —— 承载音视频数据（UDP 或 TCP）
RTCP  : RTP 控制协议 —— 统计丢包、抖动、同步
RTSP URL 例: rtsp://192.168.100.1:8554/h265
```

RTSP 本身不传数据，它像"遥控器"，真正的视频数据走 RTP。这就是为什么视频流实时性高（RTP over UDP 不重传，宁可丢帧不卡顿）。

### 4.2 live555 框架
本项目使用的开源 RTSP 服务器库。核心类关系（本项目自定义的部分）：

```
RTSPServer                 // 监听 8554 端口，处理 RTSP 请求
  └─ ServerMediaSession    // 一个会话 = 一路流（如 /h265）
       └─ OnDemandServerMediaSubsession  // 按需创建：有客户端拉流才真正开流
            ├─ FramedSource（LiveSource） // 帧数据源：从 SharedQueue 取编码包
            ├─ H265VideoStreamFramer     // 解析 NAL 单元，组装成完整帧
            └─ H265VideoRTPSink          // 打成 RTP 包发出去
```

**关键设计**：LiveSource 的 `doGetNextFrame()` 从线程安全的 `SharedQueue` 取包，取到后调用 `FramedSource::afterGetting()` 通知事件循环。编码线程推包后用 `scheduler->triggerEvent()` 唤醒 live555 事件循环立即派发——这就是编码线程和 live555 单线程事件循环之间的**跨线程通知机制**（EventTriggerId）。

### 4.3 OnDemand（按需）的意义
没有客户端观看时，编码线程照常编码（因为要 AI + 录像），但 RTSP 只维护队列；有客户端连接时才创建 FramedSource 开始消耗队列。队列有上限，**无客户端时不堆积**。

## 5. AI 推理：RKNN NPU 与 YOLOv8-Pose

### 5.1 为什么用 NPU
CPU 跑 YOLO 推理一帧几十~几百毫秒；RK3568 的 NPU（0.8 TOPS）跑 yolov8n-pose 640x640 约 30~50ms。**NPU 是专门做矩阵乘加（MAC）的硬件**，神经网络 90% 计算量是卷积（矩阵乘法），所以 NPU 能效比 CPU 高一个数量级。

### 5.2 模型部署流程（PyTorch → 板端）
```
yolov8n-pose.pt (PyTorch)
   → 导出 .onnx (通用模型格式)
   → RKNN-Toolkit 转换 + i8 量化 → yolov8n-pose.rknn
   → 板端 librknnrt.so 加载推理
```

### 5.3 量化（Quantization）—— 面试高频
模型权重原来是 float32（4 字节）；**i8 量化**把权重和激活值映射到 int8（1 字节）：
- 体积缩小 4 倍，内存带宽需求降 4 倍
- NPU 整数运算比浮点快得多
- 代价：精度略有损失（本项目用的定点反量化公式：`float = (q - zp) × scale`，zp 是零点，scale 是比例）

后处理里可见 `deqnt_affine_to_f32()` / `qnt_f32_to_affine()` 就是量化↔反量化。

### 5.4 YOLOv8 检测头原理（项目后处理实现了它）
YOLOv8 是 **Anchor-Free** 检测器（对比 YOLOv3/v5 的 Anchor-Based）：
1. 输入 640x640，输出 3 个尺度的特征图（80x80、40x40、20x20，即 8/16/32 倍下采样），共 8400 个预测点
2. 每个点预测：4 个边界框值 + 类别分数
3. **DFL（Distribution Focal Loss）解码**：边界框每条边不是直接回归一个数，而是预测 16 个概率分布，加权求和得到精确位置——这就是后处理里 `softmax(&loc[i*16], 16)` 然后 `Σ prob[i] × i` 那段代码
4. **NMS（非极大值抑制）**：多个框重叠检测同一目标时，按置信度排序，IoU 超过阈值（0.45）的低分框被抑制

### 5.5 Letterbox（信箱缩放）—— 面试高频
模型固定输入 640x640，但摄像头画面是 640x480（比例不同）。**Letterbox = 等比例缩放 + 灰边填充**：
```
scale = min(640/480, 640/640) = 1.0
新尺寸 480x640（等比），左右各补 80px 灰边 → 640x640
推理后把坐标减去 pad 再除以 scale 映射回原图
```
不直接拉伸是为了**保持目标宽高比**，检测更准。本项目用 RGA 硬件一次性完成缩放+填充（`rga_letterbox_fd`）。

### 5.6 姿态估计：17 个关键点
COCO keypoint 格式，17 个点：0 鼻子、1-2 眼睛、3-4 耳朵、5-6 双肩、7-8 双肘、9-10 双腕、11-12 双髋、13-14 双膝、15-16 双踝。每个点输出 (x, y, 置信度)。骨架连线（19 组）把点连成人形。

### 5.8 RKNN 版本体系与升级方法论（本项目实战）

**三层版本关系**（升级时逐层核对）：
```
模型格式版本（rknn-toolkit2 转换时决定）
     │ 只能被 ≥ 自己版本的 runtime 加载
     ▼
librknnrt.so runtime（板端推理库）
     │ 运行需要内核驱动支持
     ▼
内核 NPU 驱动（本项目 RKNPU driver v0.9.2）
```

**本项目升级实战**（2.0.0 → 2.2.0，AI 推理 47.5ms → 45.3ms）：
1. **runtime 换新**：2.2.0 的 librknnrt.so 替换编译链接库 + 板端部署库（注意 LD_LIBRARY_PATH 会覆盖系统库——板端 /usr/lib 已升 2.2.0 时，TLServer 仍因 `./lib` 优先在用旧的 2.0.0，这是"两个版本并存"的隐蔽坑）
2. **模型必须重转**：新 runtime 的算子优化（如 MatMul 映射到 NPU：39.4→1.2ms）只对**新格式模型**生效——旧格式模型在新 runtime 下收益极小，必须用新版 toolkit 重转
3. **驱动兼容性**：runtime 版本上限由内核驱动决定。v0.9.2 实测兼容 2.2.0 无需刷固件；2.3.x 未验证不冒险
4. **回退**：替换前备份（.bak），升级失败恢复两个文件重编译即可——嵌入式升级的标配做法

**混合量化（hybrid quantization）——本项目实战踩过的核心坑**：
- **全量 i8 量化的陷阱**：yolov8-pose 的关键点输出张量 [17,3,8400] 混合了坐标（0~640）和置信度（sigmoid 0~1）两类值域。per-tensor 量化只用一个 scale（如 3.19，为坐标设计）→ **置信度 0~1 被压缩到 zp 附近 1 个量化步长内，信息完全丢失**（反量化后恒 0）→ 无关键点、姿态判 unknown。这坑排查了整整一天
- **官方解法**（rknn_model_zoo convert.py）：`hybrid_quantization_step1/step2` + `custom_hybrid` 参数把关键点分支（DFL 卷积的输出 → Concat_6）指定**不量化**（保持 float16），其余层正常 i8。转换日志会打印 "output dtype of Concat_6 changed to float16"
- **代价**：hybrid 模型比全量化略慢（45.3ms vs 39.5ms），因为 float16 分支有转换开销——精度换性能的合理取舍
- **部署三件套验证法**：① 启动日志看输出[3] 的 type/zp/scale ② 连板推理看 conf 值域是否 0~1 ③ 画面实拍复测
- 通用规律：**任何"多值域混合张量"（坐标+概率、多任务输出）做全量化都要警惕 per-tensor scale 的适配性**

**连带收益**：连板调试链（rknn-toolkit2 2.2.1 ↔ 板端 runtime 2.2.0）版本天然匹配，pose.py 连板分析、KWS 模型部署都直接可用。

### 5.9 多分辨率模型与"导出结构漂移"（面试可讲）

**需求**：同一套代码支持 640 和 320 两种输入分辨率的模型（320 版 NPU 推理快 ~3×，低延迟场景用）。

**关键坑 1：ultralytics 版本的导出结构漂移**——同是 yolov8n-pose，不同版本 ultralytics 导出的 ONNX 结构完全不同：
- 旧版导出（rknn_model_zoo 官方）：**4 个输出**（3 个检测头各 [1,65,h,w] + 关键点 [1,17,3,8400]），DFL 解码在后处理里做（CPU softmax×16）
- **ultralytics 8.4 导出：单输出** `[1,56,N]`——**DFL 解码、sigmoid 全部内嵌进模型**（NPU 算），框直接是绝对像素坐标，conf/vis 直接是 0~1
- 所以"升级工具链"时后处理必须跟着换：单输出模型的后处理反而更简单（无 DFL、无 grid 循环），且把解码算力从 CPU 挪到 NPU

**关键坑 2：模型输出里"已 sigmoid 的值"再 sigmoid 一次**——把 0~1 的值再压到 0.5~0.73，表现为"95% 的 anchor 置信度 >0.5"的假阳性海啸。定位方法：取最大值反推 logit 与参考实现（ultralytics predict）对照。

**关键坑 3：hybrid 量化的层名随结构漂移**——320 模型无 Concat_6，需用 onnx 消费者链追踪关键点分支的真实汇合点（cv4.x → Concat_5 → output0），custom_hybrid 终点改为最终输出名。

**多分辨率后处理原则**：锚点数（2100/8400）、grid 尺寸全部从 output_attrs 的 dims 动态读，代码里零硬编码——本项目单输出路径天然满足（N = attr.dims[2]）。

**精度代价认知**：320 模型关键点置信度整体下降（实测髋部 conf 从 >0.3 降到 ~0.2），低分辨率下遮挡关键点更容易低于分类门槛——"低延迟选项"与"姿态分类灵敏度"需要按场景权衡，门槛应配置化。

### 5.7 RKNN 零拷贝推理（本项目优化）
常规 API：`rknn_inputs_set` + `rknn_run` + `rknn_outputs_get`，每次调用都拷贝数据。零拷贝 API：`rknn_create_mem` 申请 NPU 可访问内存 → `rknn_set_io_mem` 一次性绑定输入输出 → 之后用 RGA 把数据 DMA 写入该内存（`input_mem->fd`），推理结果直接落在 `output_mems[i]->virt_addr`。**全程无 CPU 拷贝**，和 V4L2 的 DMABUF 是同一个思想。

### 5.10 OSD 画面叠加（尝试后已移除，面试可讲"为什么放弃"）

**需求**：双码流左上角显示实时帧率。方案：编码前对 YUV 帧烧录文字——子码流搭 AI 绘图管线便车，主码流新增小 ROI 管线（RGA 只转换左上角 320×48 区域→CPU 画字→RGA 写回，微秒级）。

**为什么移除**：功能完整但"画了不显示"的问题难以收敛——主码流录像抽帧证明文字已烧进编码输出，CPU 读回探针证明绘制成功，但子码流 RTSP 抽帧始终无文字，写回链路（RGA RGB→NV12→rotate90→MPP）根因未定位。综合复杂度与收益，决定移除。

**沉淀的两个排查方法（面试可讲）**：
1. **同源对照**：录像与 RTSP 共用同一个编码包（编码后既 push 队列又交录像模块），"录像里有 = 推流里有"——用录像抽帧做像素分析，比抓 RTSP 流可靠
2. **CPU 读回探针**：绘制后立即读回缓冲区分"没画上"和"画了没写回"，把问题二分到 CPU 侧或 RGA/编码侧

**技术点保留**：MPP buffer 高度 stride 16 对齐（1080→1088）需用 `wrapbuffer_fd_t` 传真实 stride，否则 UV 平面错位；位图字库 fontpixelsize 过小会物理不可见；彩色文字需配黑底条对抗 4:2:0 色度子采样。

## 6. 姿态分类与跌倒检测算法

### 6.1 总体思路：多特征投票 + 连续帧确认
单帧判断不可靠（抖动、遮挡），所以：
1. 每一帧提取多个几何特征，每个特征投一票"像跌倒"
2. 票数 ≥ 阈值（2）算一帧"跌倒候选"
3. **连续 5 帧**候选 → 确认为跌倒
4. 确认后 15 秒冷却期内不重复报警

### 6.2 几何特征（每条都对应一段代码）
**特征 1：整体方向比例**（body orientation）
取 17 个关键点的外接矩形：`ratio = width / height`。站立 ≈ 0.3~0.5（瘦高），躺倒 > 1.1（宽扁）。

**特征 2：头脚连线角度**（head-feet angle）
鼻子中点与两踝中点连线，与水平线夹角：站立 ≈ 90°（垂直），躺倒 < 45°。

**特征 3：躯干倾角**（torso angle）
双肩中点与双髋中点连线，与**垂直线**夹角：站立 ≈ 0°，躯干倒下 > 45°。

**特征 4：检测框宽高比**（bbox aspect ratio）
同特征 1 但用 YOLO 输出的框而非关键点，两者互补（关键点可能缺，框总在）。

### 6.3 为什么用投票而不是单一特征
单一特征各有失效场景：弯腰捡东西（头脚角度变小但没跌倒）、侧躺被遮挡、误检框变形。**多特征多数投票**把单特征误判的概率相乘式地降低。

### 6.4 置信度门控
关键点置信度 < 0.3 的点不可信，直接跳过。如果**双肩双髋**四个核心点任一不可信，整帧判 UNKNOWN（宁可漏判不误判）。

## 7. 多人目标追踪：IoU 匹配

> （本次开发新增）

### 7.1 为什么需要追踪
没有追踪时，跌倒确认计数器是全局的：A 帧里张三摔倒投一票，下一帧里李四走路清零，再下一帧张三又投一票——**多人时投票状态互相干扰**，跌倒事件永远攒不满 5 帧，或者把不同人的票数混在一起误报。追踪让每个"人"拥有独立的投票计数器。

### 7.2 IoU（交并比）
两个框的重叠程度：
```
IoU = 交集面积 / 并集面积
     = max(0, min(x2,x2') - max(x1,x1')) × max(0, min(y2,y2') - max(y1,y1'))
       ─────────────────────────────────────────────────────────────────────
       (两框面积之和 - 交集面积)
```
IoU = 1 完全重合，0 完全不重叠。

### 7.3 贪心匹配算法（本项目实现，适合人数少、帧率高的场景）
```
上一帧追踪到的人: [A, B, C]（各带 bbox）
本帧检测结果:     [d1, d2, d3]

1. 计算 3×3 IoU 矩阵
2. 贪心：每次取全矩阵最大的 IoU 对，若 > 0.3 则配对，已配对的行列划掉
3. 配上的检测 → 继承该人的 ID 和投票状态
4. 没配上的检测 → 新人，分配新 ID
5. 没配上的旧人 → 连续失配则删除（人离开画面）
```
为什么够用：AI 帧率 ~15fps，相邻两帧同一人位移小、IoU 高；人数少（家庭场景）O(n²) 无压力。更复杂的场景才需要 Kalman 滤波（预测位置）或匈牙利算法（全局最优匹配）+ 外观特征（ReID），这些是面试扩展点。

### 7.4 逐人状态机
```
每人独立状态:
  fall_streak: 连续跌倒候选帧数, >= 5 确认跌倒
  sit_streak : 连续坐姿帧数,     >= 3 显示为"坐姿"
  last_alarm : 该人上次报警时间（15s 冷却）
确认跌倒 → 生成事件（person_id + 该人自己的检测置信度）
全局额外 15s 冷却：防止同一个人 ID 丢失重分配后重复报警
```

## 8. 坐姿检测特征

> （本次开发新增）

### 8.1 站立 / 坐姿 / 躺倒的几何区别
| 状态 | 躯干（肩-髋连线） | 大腿（髋-膝） | bbox 宽高比 |
|---|---|---|---|
| 站立 | 垂直 | 垂直向下 | ~0.3-0.5（瘦高） |
| 坐姿 | **垂直** | **接近水平** | ~0.75-1.15（偏方） |
| 躺倒 | 水平 | 水平 | >1.15（宽扁） |

关键洞察：**坐姿的躯干是直的，区别在腿的折叠**。所以先判跌倒（躯干倒了），没倒再看腿：

### 8.2 三个坐姿投票特征
设 torso_len = 肩中点与髋中点的垂直距离（躯干长度），y 轴向下为正：
1. **bbox 宽高比** ∈ [0.75, 1.15]：比站立宽（坐姿人变矮变宽），但没躺倒那么宽
2. **大腿折叠比** = (膝中点y − 髋中点y) / torso_len：站立 ≈ 0.6~0.9，坐姿 < 0.5（大腿接近水平，垂直投影短）
3. **踝髋折叠比** = (踝中点y − 髋中点y) / torso_len：站立 ≥ 0.9，坐姿 < 0.75（小腿收在椅子下方）

≥2 票 → 本帧坐姿。决策顺序：**先判跌倒，再判坐姿，否则站立**（跌倒优先级最高，安全第一）。

### 8.3 阈值从哪里来
几何推导 + 真机数据标定。`pose_classifier.cpp` 里所有阈值都 `#define` 在文件顶部，方便调参。`ai_debug.log` 每帧输出全部特征值，标定时看日志找分界点。

## 9. MQTT 报警通信

### 9.1 为什么用 MQTT
监控报警场景：设备要主动把事件推给服务器/手机。HTTP 是"请求-响应"模型（设备要轮询或开服务器）；**MQTT 是发布/订阅模型**，设备作为 publisher 把报警发到 broker（消息中间件），手机/服务器作为 subscriber 实时收到，天然适合物联网。

### 9.2 核心概念（面试高频）
- **Broker**：消息中转服务器（如 mosquitto，本机 192.168.5.77:1883）
- **Topic**：消息主题，`home/fall`，订阅者按主题过滤
- **QoS 等级**：
  - QoS 0：发一次，不确认（可能丢）
  - QoS 1：**至少一次**（本项目用）—— 接收方回 PUBACK，没收到就重发，可能重复
  - QoS 2：恰好一次（四次握手，开销大）
- **Retained（保留消息）**：broker 保存该主题最后一条消息，新订阅者一上线立刻收到（本项目 retained=1：新开的手机 App 能立刻看到最近一次报警状态）
- **KeepAlive**：定期心跳（15s），超过 1.5 倍无心跳 broker 判定设备掉线
- **CleanSession**：0 = 会话持久（掉线期间 broker 帮存 QoS1 消息）

### 9.3 本项目 MQTT 线程设计（可靠性三件套）
1. **异步队列**：AI 线程把事件 `mqtt_push_event()` 入队即返回，绝不阻塞推理；独立 MQTT 线程消费
2. **指数退避重连**：断线后 1s→2s→4s…→60s 重试，失败间隔翻倍（避免疯狂重连打爆网络）
3. **失败回队 + 强制重连**：`waitForCompletion` 等待 QoS1 ACK，超时视为失败，事件放回队首，下次重发；连续失败判定连接假死，主动断开重建
4. 队列上限 100，满则丢最旧（报警宁丢旧的不堵新的）

### 9.4 报警消息 JSON 格式（本次新增图片）
```json
{
  "event": "fall",
  "device_id": "rk3568_home_001",
  "timestamp": "2026-08-17 14:30:05",
  "confidence": 0.85,
  "image": "/events/image/fall_20260817_143005_3.jpg",
  "image_base64": "/9j/4AAQSkZJRg...",     // 320px 缩略图 JPEG 的 base64
  "video": "/mnt/sdcard/record_main/events/20260817/143005_003_fall.h265"
}
```

### 9.5 Base64 编码（本次新增）
MQTT 是文本协议，不能直接传二进制图片字节，所以用 **Base64**：把每 3 字节（24 bit）拆成 4 个 6 bit，每个 6 bit 映射到 64 个可打印字符表（A-Z a-z 0-9 + /）。体积膨胀 4/3 ≈ 1.33 倍。

流程：`cv::imencode()` 把抓拍画面编码成 JPEG 字节流（约 20KB@320px）→ base64 变文本（约 27KB）→ 塞进 JSON 发送。接收端（手机/服务器）base64 解码即得图片。**为什么用缩略图**：640x480 原图 base64 约 60-100KB，MQTT 大消息易超 broker 限制、慢；320px 足够看清现场，原图留在板端 SD 卡（image 路径字段）。

**JSON 转义注意**：路径含 `"` 等字符会破坏 JSON，本项目路径由自己生成（时间+序号）不含特殊字符，所以未做转义（简化）。

## 10. 事件存储：SQLite + 异步落盘

### 10.1 为什么用 SQLite
板端要持久化事件记录（时间/类型/置信度/图片路径），SQLite 是**嵌入式数据库**：单文件、零配置、无需服务器进程，嵌入式设备首选（对比 MySQL 太重）。

### 10.2 表结构
```sql
CREATE TABLE events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  event_type TEXT,        -- 事件类型: "fall"
  device_id TEXT,         -- 设备编号
  confidence REAL,        -- 置信度
  timestamp INTEGER,      -- unix 时间戳
  image_path TEXT,        -- 抓拍图本地路径
  video_path TEXT,        -- 事件录像本地路径
  upload_status INTEGER DEFAULT 0  -- 上传状态（预留字段，后续做云端同步用）
);
```

### 10.3 异步落盘设计（单生产者单消费者）
AI 线程是性能热点，**绝不能**在里面同步写磁盘（SD 卡写延迟可能几十 ms）。所以：
- AI 线程把（事件 + 图片）扔进队列（上限 100，满丢最旧）
- EventManager 专属 worker 线程串行处理：存图 → `INSERT` 落库
- **单消费者 = SQLite 连接天然线程安全**，不需要考虑并发写
- 本次优化：图片改为事件线程**同步保存**（拿到路径立即填进 MQTT 消息），worker 线程只负责 DB 插入

### 10.4 为什么用预处理语句（Prepared Statement）
`sqlite3_prepare_v2` + `sqlite3_bind_text` 而不是字符串拼接 SQL：
1. **防 SQL 注入**（值永远当数据处理，不当代码执行）
2. **性能**：SQL 只解析一次，之后复用执行计划
3. **类型安全**：int/real/text 明确绑定

## 11. 录像系统：切片 / 预录 / 参数集

### 11.1 两类录像
- **连续循环录像**：5 分钟一个切片文件，写满 SD 卡自动删最旧（水位 85%）——监控"黑匣子"模式
- **事件录像**：跌倒触发，**前 5 秒（预录）+ 后 5 秒** 独立存一个文件

### 11.2 预录的实现：环形缓冲
```
编码线程每输出一帧 → 拷贝进 deque 环形缓冲
缓冲只保留最近 5 秒（按时间戳剪头）
跌倒触发 → 把缓冲里的旧帧从最近的 IDR 帧开始写入事件文件
         → 之后的帧边编码边续写（后 5 秒）
```
**为什么要从 IDR 帧开始**：解码器必须从 IDR 才能解出画面（见 3.4）。预录缓冲里如果没有 IDR，文件前几帧就是废的。

### 11.3 参数集注入
MPP 周期性（每个 IDR 附近）输出 VPS/SPS/PPS。切片文件是"半路截取"的，开头不一定有参数集 → 文件无法播放。解决：编码器启动时把第一次拿到的参数集缓存下来，**每个新文件开头先写一份参数集**（`writeHeadersToFile`）。同时用 `stripInlineParamSets` 把码流里内嵌的参数集剥离，避免重复——这是本项目踩过的坑。

### 11.4 音频采集与 AAC 编码（ALSA → fdk-aac）

**采集链**：板载 RK809 codec（ALSA 设备 `hw:0,0`）→ 独立采集线程 `audio_cap`（nice 10 低优先级）→ 16kHz/2ch/S16_LE（RK809 最小 2 声道）→ 多 sink 分发（录像、RTSP、未来 KWS 关键词识别）。

**为什么用 ALSA 阻塞 readi 而不是 poll**（本项目踩过的坑）：ALSA 的 poll 描述符在**流未启动**（`snd_pcm_start` 或首次 readi 之前）时永远等不到 POLLIN 事件——采集线程会静默饿死。正确姿势是显式 `snd_pcm_start` 后使用阻塞 `snd_pcm_readi`（period=50ms 保证每次调用 ≤50ms 返回），停止时用 `snd_pcm_drop` 打断阻塞，保证线程退出有界。

**AAC-LC 编码（fdk-aac，静态链接进 TLServer）**：
- 参数：16kHz **单声道**（内部 (L+R)/2 降混）、24kbps、AFTERBURNER 质量增强
- **帧对齐问题（面试点）**：AAC-LC 每帧固定 **1024 样本**，16kHz 下 = 64ms/帧，而采集块是 50ms——两者不对齐。解法：**降混累加缓冲**（mono_buf_），攒满 1024 样本才调 `aacEncEncode`，帧时间戳 = 缓冲首样本时刻
- 输出**裸 AAC AU**（TRANSMUX=0，无 ADTS 头）——MP4 和 RTSP 都用这个格式
- **ASC（AudioSpecificConfig）**：编码器 confBuf 提供（16kHz mono AAC-LC = `0x14 0x08` 两个字节），同时喂给 MP4 的 esds 和 RTSP 的 SDP `config=` 参数。位布局：AOT(5bit) + 采样率索引(4bit) + 声道配置(4bit)——本项目曾踩坑 0x1388（那是 22050Hz 的索引）
- CPU 成本：16kHz mono 单帧编码 <0.3ms（占 50ms 采集周期的 <1%），在采集线程内联完成，不新增线程

**音频码率对比**：裸 PCM 64KB/s vs AAC-LC 24kbps = **3KB/s**，音频体积从 5.4GB/天降到 ~260MB/天（主码流的 +0.6%）。

### 11.5 MP4 封装与业界方案对比（面试常问）

**本项目的演进**：裸流 `.h265+.wav`（一期）→ **fMP4 + AAC（二期，当前）**。为什么最终还是要上 MP4：用户要"双击即播"的产品体验；而朴素 MP4 的 moov 在文件尾、掉电全废的问题，用 **fMP4（fragmented MP4）** 解决：

**fMP4 核心原理（本项目 minimp4 实现）**：
```
文件布局: ftyp | moov(含 hvcC/esds/mvex) | moof#1+mdat#1 | moof#2+mdat#2 | ...
              ▲ 首个样本时立即写入文件头         ▲ 每个样本一个独立分片
```
- **moov 在文件头**（传统 MP4 在文件尾）→ 文件从第一秒起就可播放
- **每个 moof 分片自包含** → 掉电只丢最后一个未写完的分片，其余完好（本项目 kill -9 实测：270s 录像完整可读）
- 配合 5 秒周期 fsync（现有掉电保护机制复用）

**minimp4 两个工程细节**：
1. **duration 制而非 PTS 制**：`MP4E_put_sample(轨道, 数据, 时长, kind)`，PTS = 之前所有样本时长累加。好处：**事件预录段先写入即成为 t=0，不存在负 PTS 问题**（若用 PTS 制，预录段 PTS 为负需偏移处理）
2. **官方 h26x writer 按 NAL 写样本的坑**：每个 slice NAL 都计一个 duration，MPP 若一帧多 slice 会时长膨胀 → 自封装每帧单样本（annex-B → length-prefixed 拼接），duration = 相邻帧 PTS 差

**主流产品对比**（海康/大华/GoPro/行车记录仪都是 fMP4 + AAC 这条路）：
| | 一期（裸流对） | 二期（fMP4+AAC，当前） | 主流产品 |
|---|---|---|---|
| 容器 | 无（.h265+.wav） | fMP4 (minimp4) | fMP4（各家实现） |
| 音频 | PCM 64KB/s | AAC-LC 3KB/s | AAC-LC（硬件编码器） |
| 掉电 | 天然鲁棒 | 分片+fsync 鲁棒 | 同左 + 电池/UPS |
| 播放 | 需 remux | 双击即播 | 双击即播 |

**RTSP 音频推流（本期新增）**：live555 `MPEG4GenericRTPSink`（RFC 3640），SDP `a=rtpmap:96 mpeg4-generic/16000/1; a=fmtp:96 config=1408`。要点：sink 自动生成 4 字节 AU header，外部只需每帧交付一个完整裸 AAC AU + 提供 ASC 十六进制串。板端实测 `ffprobe rtsp://板IP:8554/h265` 返回 hevc+aac 双流。客户端（QT/ffmpeg/VLC）拉流即可得音视频——PC 端 QT 播放音频是下期工作（VideoDecoder 的音频注入点已探明：`VideoDecoder.cpp` 的音频包丢弃分支 + QAudioSink）。

**音频 AI（关键词识别）预留**：AudioCapture 的多 sink 架构天然支持——KWS 模块作为第 3 个 PCM sink（16kHz mono 正是 KWS 模型标准输入），配置开关 `audio_kws_enable`，命中后走现有 `mqtt_push_event` 报警链路（二期实现识别逻辑，本期空占位）。

**主流产品（海康/大华/萤石/小米/Tapo/GoPro/行车记录仪）**：板端直接录 **MP4 单文件**，音视频 mux 在一起，音频用 **AAC-LC**（16kHz 单声道约 16~24kbps，是 PCM 的 1/5~1/8；海思/安霸等 SoC 多有**硬件 AAC 编码器**，零 CPU 成本）。

但朴素 MP4 有个致命伤：`moov` 索引头写在**文件末尾**，录制中途断电 → moov 没写完 → **整个文件报废**。产品的解法：
1. **fMP4（fragmented MP4）**：文件切成自包含的 `moof` 分片，边录边可播放，掉电只丢最后一个分片（几秒）
2. **渐进式 moov**（GoPro 风格）：录制中定期更新 moov 头——和本项目 WAV 头"5 秒回填"是同一个思想
3. 底层配合：ext4 日志 + 周期 fsync + SD 卡水位循环覆盖
4. 分工：很多安防相机**自己不录像**，RTSP 推给 NVR 统一录（封装/保留策略由 NVR 负责）

**本项目的"裸流 + 同名 wav"对应什么**：原始流存档风格——工程极简、CPU 零开销、掉电天然鲁棒（裸流损坏只丢局部，无需 fMP4 那套复杂设计），代价是播放需后处理（PC 端 `merge_av.py` 秒级 remux 成 MKV）。这是"学习/自用/快速打样"定位下的合理选择；朴素 MP4 才是两头不占（又要 mux 又怕掉电）。

**升级到产品级的路径**：板端引 fdk-aac 软编（RK3568 无硬 AAC，约 3~5% 单核）+ 轻量 fmp4 muxer（如 libfmp4/minimp4），音频码率从 64KB/s 降到 ~3KB/s；掉电保护改为 moof 分片 + 渐进 moov。是否值得，取决于产品定位（自用 → 不值得；要出货 → 值得）。

### 11.6 SD 卡可靠性与掉电保护
- **开机自检**：写 8MB 测试文件 → 回读校验 → 测写速（≥2MB/s），不合格直接禁用录像（假卡/坏卡常见于嵌入式）
- **掉电保护**：缓冲 4MB 的用户态缓冲（`setvbuf`）+ 每 5 秒 `fflush` + `fsync`（强制刷到物理介质），断电最多丢 5 秒
- 原始 H.265 裸流存 `.h265` 文件（没封装 MP4，封装需要额外库，且掉电时 MP4 的 moov 头没写完整个文件全废——裸流损坏只丢局部）

## 13. PC 客户端：FFmpeg + QT

### 13.1 拉流与硬件解码
FFmpeg 的 `avformat` 打开 RTSP URL → 找视频流 → `avcodec` 解码器。**cuvid** = NVIDIA 的硬解 API（用 GPU 解码 H.265，CPU 占用几乎为零，对比软解 H.265 1080p CPU 占用可达几十 %）。

### 13.2 录像零开销技巧：Remux
客户端录像**不做解码重编码**：直接把 RTSP 收到的 H.265 码流按 MP4 容器格式重新封装（remux）。重编码 = 解码 + 编码（CPU/GPU 重负载 + 画质损失），remux 只是换个"外壳"，成本极低。

## 14. 多线程设计与并发模型

TLServer 同时运行 7+ 个线程，是很好的并发学习案例：

| 线程 | 职责 | 同步机制 |
|---|---|---|
| main | live555 事件循环（单线程模型） | EventTriggerId 跨线程唤醒 |
| h265_enc / h264_ai_enc | 采集+编码 | SharedQueue（mutex+condvar） |
| h264_ai | RKNN 推理 + 姿态分类 + 追踪 | ai_queue + free_ai_bufs 双队列 |
| event_proc | 事件落盘/MQTT 组装 | event_queue (mutex+condvar) |
| recorder | 写录像文件（视频+音频，唯一写线程） | packet_queue + audio_queue + cmd 队列 |
| audio_cap | ALSA 音频采集（阻塞 readi + 环形预录缓冲） | 内部 ring_mtx_，snd_pcm_drop 打断退出 |
| mqtt | 报警发送 | mqtt_queue |

### 14.1 都用到的"生产者-消费者"模式（面试高频）
```
生产者: lock; queue.push(x); unlock; cv.notify_one();
消费者: unique_lock lk(m); cv.wait(lk, []{ return !q.empty() || exit; });
```
为什么 condvar 必须配合 mutex？避免"检查队列空 → 准备睡眠"之间生产者插入导致唤醒丢失。`wait` 的谓词版本（lambda）防**虚假唤醒**（spurious wakeup）。

### 14.2 丢帧策略（实时系统核心思想）
所有队列都有上限，满了**丢最旧帧**（视频）或丢最旧事件。**宁可丢数据不可堆积延迟**——监控画面要的是"最新"而不是"全部"。AI 输入还有双队列设计：空闲缓冲池 + 待处理队列，推理忙时直接跳过抽帧（不排队旧帧），保证推理的永远是最新画面。

### 14.3 看门狗（健康监控）
`monitor` 线程每秒检查两个编码线程的存活标志（RAII：`ThreadAliveGuard` 构造置 true、析构置 false）。编码线程异常退出 → 2 秒后 `abort()` → 由 init 脚本守护自动重启进程。**嵌入式设备不追求不崩溃，追求崩溃后快速自愈**。

### 14.4 锁的粒度与死锁预防
- 锁的粒度尽量小（只保护队列本身，不包住耗时的推理/IO）
- 事件线程拿 VideoRecorder 结果、AI 线程只碰自己的队列，模块间用原子变量（`pending_fall`）传简单状态
- 单例（EventManager/Logger/VideoRecorder）内部自管理线程生命周期，`shutdown()` 置 running=false + notify_all + join

### 15.1 rknn-toolkit2 连板调试（--npu_device_test）
rknn-toolkit2 在 PC 上安装（conda 环境 `python3.8-tk2-2.2`），通过 **adb 连接开发板**，把推理引擎（librknnrt）推送到板子上运行：

```bash
python pose.py --target rk3568 --npu_device_test \
    --model model/yolov8n-pose.rknn --eval_perf
```

- `--npu_device_test`：在**真实 NPU** 上跑（不加则在 PC 上用模拟器跑，耗时无参考意义）
- `--eval_perf`：逐算子耗时分析（Operator Time Consuming Ranking Table）
- `--eval_memory`：内存占用评估
- `--accuracy_analysis`：量化精度分析（对比 fp32 参考输出，看哪些层量化损失大）

**为什么能连板**：PC 负责模型加载/预处理/后处理，RKNN 运行时通过 adb 把 `inference` 请求发给板端 NPU，结果回传。这就是"PC 调试 + 板端真实算力"的开发模式。

### 15.2 实测数据（本项目 RK3568，2026-08-17 连板）
yolov8n-pose 640x640 i8 单帧推理 **45.9ms ≈ 22fps** 上限：
| 算子 | 耗时 | 占比 | 说明 |
|---|---|---|---|
| ConvExSwish | 25.2ms | 54.9% | 卷积+SiLU 激活融合算子，NPU 主力 |
| Reshape | 8.7ms | 19.0% | **CPU 算子**（8.7/8.9ms CPU 时间几乎全在这） |
| Concat | 4.1ms | 9.0% | NPU |
| 其余 | 7.9ms | 17.1% | Add/Split/Conv 等 |

**面试看点**：为什么 Reshape 是 CPU 时间大头？Reshape 只是"换元数据视角"不应耗时——说明模型里存在**数据搬运**（如 transpose），被量化工具合并成了 Reshape 节点。优化方向：换模型结构或让转换器融合掉该节点。

### 15.3 阈值标定的正确姿势：调用真代码，不写镜像
标定姿态分类阈值时，一个常见错误是"用 Python 重写一份分类逻辑来调参"。问题：**两份逻辑必须手动同步，迟早漂移**。

本项目的做法（工具在 `server/tools/`）：
```
pose.py --dump dump.npz          # 连板跑真实 .rknn，导出每个人(框+17关键点)
       ↓
libpose_classify.so              # pose_classifier.cpp 用本机 gcc 直接编成动态库
       ↓                          #   （C++ 编译成 .so，不需要交叉工具链）
calibrate_pose.py --dump dump.npz  # ctypes 调用 .so 里的真 C++ 函数批量分类
       ↓
ai_debug.log 解析 → 特征分布统计 / CSV 导出 → 在 Excel 里看分布定阈值
```

**原理**：`pose_classifier.cpp` 只依赖纯头文件（rknn_api.h 是 C 头文件声明，不链接 NPU 库），所以本机 gcc 就能编。Python 通过 **ctypes**（C 函数调用接口）直接调 C++ 编出来的函数——**阈值只活在 C++ 一处**，标定结果=板端行为。

### 15.4 合成关键点自检的定位
合成关键点（手工摆坐标）**不能用来标定阈值**（数据太理想化），但能快速验证投票逻辑的算术（5 个合成用例：站立/坐姿/躺倒/低置信度/缺关键点）。真正标定必须用**真实模型的真实输出**——本项目已用连板 bus.jpg 验证：2 人正确判 normal，1 人被遮挡者右肩置信度 0.299 卡在 0.3 门控线上被保守判 unknown（符合"宁可漏判不误判"的设计）。

### 15.6 实战排障：VLC 播放无声（链路排查方法论，面试可讲）

**现象**：板端录制的 MP4 和 RTSP 推流在 VLC 里都没有声音；换 Windows 自带播放器直接"打开文件失败"。

**排查过程（逐段验证法——从源头到终端每段都验证，而不是瞎猜）**：
1. **录制端**：板端 MP4 用 ffmpeg `volumedetect` 分析 → mean -17.9dB，**有真实音频内容** → 录制正常
2. **编码/封装端**：PC ffmpeg 完整解码 58.3s 音频（93 万样本无丢失）；ffprobe 检查 MP4 结构（双轨、时间戳连续、时长对齐）→ **文件 100% 标准**
3. **推流端**：板端回环 `ffprobe rtsp://127.0.0.1:8554/h265` 确认 SDP 双流 + ffplay 实际播放无解码错误 → RTSP 正常
4. **结论**：链路全程正常 → 问题锁定在**播放端兼容性**：VLC 对 **16kHz 低采样率 AAC** 音频轨支持不良（部分版本音频输出/重采样链路对非 44.1k/48k 采样率处理异常）。"其他播放器打不开"是另一回事：Windows 自带播放器缺 **HEVC 解码扩展**（微软商店付费，所有 H.265 文件都如此）

**修复**：采样率 16kHz → **44.1kHz**（播放器兼容性最好的采样率，且用户 arecord 实测硬件路径正常）→ VLC 恢复正常。附带收获：实测麦克风是单声道接在声道 0，原 (L+R)/2 降混白损 6dB 信噪比 → 改为配置化单声道提取（`audio_mono_source=1`）。

**方法论总结（面试答题模板）**：
- "播放端没声音"要**先证明数据是好的**（volumedetect 看音频电平、ffprobe 看轨道结构），再怀疑播放器——否则会在正确的链路里瞎改
- 嵌入式音视频的兼容性陷阱：**低采样率（16k）在专业工具（ffmpeg）里正常、在消费级播放器（VLC）里可能异常**——产品化应优先选 44.1k/48k
- 板载麦克风常见是单声道接一个声道，降混前先确认声道内容

### 15.7 音频降噪与分辨率优化的工程实践

**底噪问题的三层处理（面试可讲）**：
1. **硬件增益**（首选）：官方文档提示"降低捕获音量"——但需确认驱动是否暴露增益控制（`amixer contents` 查 Capture Volume/PGA；本项目 RK809 驱动未暴露，无法调）
2. **软件降噪**（本项目方案，AacEncoder 内）：
   - **高通滤波**：二阶 Butterworth（fc=120Hz，-12dB/oct）——对低频干扰族整体压制（比一阶 -6dB/oct 陡一倍）
   - **陷波器组（Notch Filter）**：RBJ 二阶 IIR，Q=10（带宽≈f/10），配置化频率列表。**关键教训**：嵌入式系统里的周期性干扰往往是"脉冲串"（如摄像头 30fps 帧时钟经电源耦合进麦克风），其频谱是**基频+全部谐波族**（30/60/90/…/360Hz）——只陷基频没用，谐波是独立分量，必须对族内各频点逐个陷波（本项目配置 8 个：30/50/60/90/100/120/150/180）。**但注意边界**：300Hz 以上是语音共振峰 F1 区，不能陷（伤语音清晰度）——软件降噪的极限就是"低频干扰族可清、高频残留靠语音掩蔽"
   - **噪声门限（Noise Gate）**：|样本| < 阈值 → 置 0。**局限**：只滤低电平信号，对幅度大的周期干扰无效（这就是为什么用户调阈值没用的原因——要先陷波再门限）
   - 定位方法（方法论）：拉录音 → FFT → 看频谱峰是否成整数倍关系 → 确定干扰源类型（工频=50Hz 族、帧时钟=帧率族）→ 针对性陷波
   - 阈值选择：16bit 满幅 32768，底噪一般 100~500，取 300 起步按实测调
3. **AAC 心理声学**：编码器本身会掩蔽部分低电平噪声（被动收益）

**主码流 5MP → 1080p 的决策**：
- 现象：VLC 拉流延时高、播放帧率低。**根因不在编码端**（板端 Cap=Enc=30fps 正常），而在：① 5MP@30fps 用 4Mbps 码率不足（5MP 合理码率 8~10Mbps）② PC 端 VLC 软解 5MP HEVC 压力大丢帧
- 方案：改 [main_stream] 分辨率 1920x1080（stride 1920×1088，NV12 高度 16 对齐）。**零代码改动**——V4L2 `S_FMT` 直接请求 ISP 缩放输出（IMX335 的 rkisp mainpath 支持，实测 S_FMT 成功、录像 30.0fps 满帧）
- 判断"卡顿在编码端还是解码端"的方法：看板端日志 Cap/Enc 是否满帧——满帧说明编码端健康，卡顿在传输/解码端

## 16. 语音 AI：zipformer 流式语音识别（呼救关键词检测）

### 16.1 为什么是"流式语音识别"而不是"关键词唤醒（KWS）"

需求：老人喊"救命/来人"时上报 MQTT。两条路线：
- **KWS**（关键词唤醒）：模型小（<1MB）、专门识别固定几个词；但官方 rknn_model_zoo 无 demo，中文数据要自己录
- **流式 ASR**（zipformer）：连续转文字 → 文本里搜关键词。官方支持（zipformer-bilingual-zh-en-t，中英双语）、语义最强（可扩展"疼/摔了/帮帮我"任意词，改 config 即可，不用重训模型）、RK3568 实测 RTF 0.116 完全实时

### 16.2 Transducer 架构（面试高频：对比 CTC/Attention）

zipformer 是 **RNN-Transducer（RNN-T）** 结构，三个模型协同：
- **encoder**（最大）：音频特征 → 编码。**流式关键**：它带"状态缓存"——本项目的 rknn 模型有 **36 个输入/36 个输出**，输入 1~35 是 5 层 zipformer 的缓存状态（cached_len/key/val/conv 等），每 chunk 推理后**输出 1~35 必须回填到输入 1~35**，下一 chunk 才能接上。这就是"流式"的本质：状态跨 chunk 传递，而不是每 chunk 独立识别
- **decoder**（小）：已解码 token 序列（上下文 2 个 token）→ 隐状态。每出一个新词跑一次
- **joiner**（小）：encoder 当前帧 + decoder 隐状态 → 6254 维词表 logits，取 argmax（**贪心搜索**，无 beam search——官方实现如此，6254 维 beam 太贵）

对比记忆：CTC（如 wav2vec2）是"一帧一字符"的单调对齐，无语言模型先验；Attention（如 whisper）全局注意力、无法流式；**RNN-T 用 joiner 把"声学"和"语言"两个信息流逐帧融合，天然流式**。

### 16.3 流式分块（chunk）机制

- fbank 特征：**80 维 mel 滤波器组**、帧长 25ms/**帧移 10ms**（1 秒音频 = 100 帧）
- chunk：**每 103 帧（1.03s）**送入 encoder，encoder 输出 24 帧（/4 下采样，40ms/帧）
- **hop 96 帧（0.96s），与 chunk 重叠 7 帧**——重叠是流式精度与"上下文窗"的折中
- 贪心循环：24 个输出帧逐个跑 joiner，argmax 非 blank(0)/unk(2) → 更新 decoder 上下文 → 再跑 decoder

### 16.4 工程难题（本项目流式化的核心，面试可讲）

1. **重叠 hop 导致水位必然增长**：每 chunk 消费 103 帧只前进 96 帧，音频以 100 帧/s 到达 → 未消费帧以 ~7 帧/s 永续积累。解法：**水位策略**——积压 ≥ 103+96 时跳一轮（丢 0.96s），每 ~15s 跳一次，损失 ~7% 音频，对关键词检测可接受。官方 demo 一次性喂完 wav 所以没有此问题，**只有长时流式才会暴露**
2. **采样率不匹配**：板端采集 44.1kHz/2ch（VLC 兼容），ASR 要 16kHz mono。kaldi-native-fbank 不内置重采样 → 自写**流式线性插值重采样器**（相位状态跨块连续，44.1k→16k 比率 2.75625）
3. **静音门控**：AudioCapture 的静音检测（标准差 <100）为真时丢弃 PCM 不喂 fbank → 静音时 NPU 零额外占用
4. **BPE 分词陷阱**："救命"在词表里可能被切成"救"+"命"两个 token（▁ 是词边界符）——关键词匹配必须在**拼接后的文本**上做，不能逐 token 匹配
5. **链接坑**：kaldi 预编译静态库未开 -fPIC，buildroot 工具链默认 PIE → 重定位错误；解法 `-no-pie`
6. **NPU 并发**：四个 rknn_context（pose + ASR 三模型）共用一个 NPU，任务串行。实测在线 RTF 0.466（离线独占 0.224），pose 推理 48→50ms 基本无感

### 16.5 验证方法论（离线自检法）

集成三模型最容易错的是**状态回填**（36 个张量、4D 状态要 NCHW→NHWC 转置）。验证法：给引擎加 `runOfflineWav` 离线入口，用官方 test.wav（5.61s 中文语音）跑一遍，**识别文本与官方 demo 输出完全一致 = 三模型/回填/贪心/词表全对**——不依赖麦克风、可回归、可自动化。离线通过后再验在线链路。

## 17. 端云语音对话:HTTPS 直连 LLM + TTS(业界标准架构)

### 17.1 架构与选型(面试可讲)

智能硬件接入云端 LLM 的**业界标准**:设备端 ASR → **HTTPS/WebSocket 直连云端** → LLM 流式回复 → TTS 流 → 端侧播放。MQTT 只做控制信令(注册/状态/告警),语音对话数据不走 MQTT。本项目按此架构:zipformer ASR(端侧)→ DeepSeek(流式 SSE)→ 火山 TTS → ALSA 播放。个人项目权衡(文档注明):API key 明文落板 + 跳过 TLS 证书校验;商用必须服务端中转 key 或加密存储 + 带 CA bundle。

### 17.2 自研最小 HTTPS 客户端(无 curl 环境的做法)

板端 buildroot 无 curl/无 CA 包,但有 OpenSSL 1.1 → 手写 TCP + OpenSSL(~400 行):
- **TLS**:`TLS_client_method` + `SSL_set_tlsext_host_name`(SNI,不设可能被网关拒)+ 非阻塞握手 poll 超时
- **三档超时**:连接 10s / 流空闲 15s(每次 SSL_read 的 poll 等待)/ 请求总 60s——流式接口必须有流空闲超时,否则断流挂死
- **chunked 解分块**:`Transfer-Encoding: chunked` 按 `<hex>\r\n<data>\r\n` 逐块读,0 块+空行结束;SSE 的 `data:` 行解析必须建立在解完分块的字节流上
- **不发 Accept-Encoding** → 服务端不 gzip,省解压
- **每请求新建连接**(Connection: close):对话间隔远超 keep-alive 时限,复用无意义

**本项目实战踩坑(面试好故事)**:自研 HTTP 客户端必须先在 PC 上写独立测试程序连真实 API 对比 curl 验证——chunked 读取函数把"增量"误实现为"目标大小",导致小 chunk 全部被跳过、SSE 流永远收不到 `[DONE]`,板端日志只显示"SSE 流未正常结束"。PC 测试程序一次复现定位。

### 17.3 SSE(Server-Sent Events)流式解析

DeepSeek 流式响应:`data: {json}\n\n` 逐事件;`choices[0].delta.content` 是增量文本(首 chunk 可能只有 role);`data: [DONE]` 字面量结尾(须 trim \r);`:` 开头是注释/keep-alive 行须忽略。**v4 模型默认思考模式**:先流 `reasoning_content`(思考过程,content 为 null)再流正文,陪伴场景要快 → `"thinking":{"type":"disabled"}` 关闭(实测回复 1.7s)。

### 17.4 语音对话状态机与回声消除

```
IDLE --唤醒词("你好")--> AWAIT_QUERY(10s无输入退回) --说话段落(静音2s判段)--> 
BUSY(LLM SSE → TTS → ALSA播放) --完成--> AWAIT_QUERY(60s无说话退出,多轮)
```

- **回声消除(自说自话死循环的解法)**:TTS 播放时喇叭声被 mic 录回 → ASR 会把自己的话识别成新问题。三重防线:①PLAYING+播放尾 2s 在 ASR 的 token 入口直接丢弃(suppress 门控;尾 2s 是因为 ASR 攒帧+推理有 ~1.5s 延迟);②BUSY 期间段落丢弃(不支持抢话);③静音门控辅助
- **唤醒词与呼救词分离**:唤醒词进 ASR keywords 匹配(复用机制),但 MQTT 上报回调过滤唤醒词(它只唤醒对话,不是呼救事件);每词独立冷却(唤醒 10s/呼救 30s),否则对话中"你好"反复触发
- **多轮**:messages 历史(上限 12 条)+ 固定 system 提示词(简短口语化)

### 17.5 火山 TTS 接入要点

- 鉴权:`Authorization: Bearer;<token>`(**分号**,不是空格——文档易错点)
- 成功码 `code==3000`(HTTP 200 不代表成功,业务码才是)
- 音频在 JSON `data` 字段 base64(非二进制流),encoding=wav 直接写盘;rate 仅 8k/16k/24k
- **音色与开通服务版本绑定**:TTS 2.0 服务的音色是 `_uranus_bigtts` 系列,旧 `_moon_bigtts` 音色在未开通的旧服务上报 403
- 播放:ALSA `snd_pcm_open("default")`(dmix 自动转率,任意 wav 可播)+ wav 头驱动参数

## 附录 A：面试高频问题速查

**Q1：说说零拷贝在你们项目里体现在哪？**
A：V4L2 DMABUF（摄像头 DMA 直写 MPP 缓冲）、RKNN 零拷贝 IO（RGA DMA 直写 NPU 输入内存）。核心是 dma-buf 共享物理内存，CPU 不参与拷贝。

**Q2：为什么用双码流？**
A：主码流高清给人看/录像，子码流低清给 AI——AI 不需要高清，低分辨率 NPU 推理快、带宽省；ISP 硬件同时输出两路，零额外成本。

**Q3：RTSP 和 HTTP 流媒体的区别？**
A：RTSP 是控制协议+RTP 传输，面向实时（低延迟、UDP 可丢帧）；HTTP 流（HLS/DASH）是切片文件下载，面向兼容性（可过 CDN、延迟高）。

**Q4：跌倒检测怎么防误报？**
A：① 关键点置信度门控 ② 多特征投票（4 特征 ≥2 票）③ 连续 5 帧确认 ④ 15 秒冷却 ⑤ 多人时逐人独立计数（追踪）。层层过滤。

**Q5：MQTT 怎么保证报警不丢？**
A：QoS1（至少一次）+ waitForCompletion 等 ACK + 失败回队重发 + 断线指数退避重连 + retained 消息让新订阅者补收。

**Q6：GOP、I 帧、IDR 的关系？**
A：GOP = 两个关键帧间隔。I 帧 = 帧内编码（完整画面）。IDR = I 帧的一种，且清空参考帧缓冲，只有 IDR 能作为随机访问点。录像切片必须从 IDR 开始。

**Q7：量化是什么？为什么 NPU 用 int8？**
A：float32→int8 映射（scale/zero-point 仿射变换），模型小 4 倍、整数运算快、带宽省，精度损失可接受。

**Q8：IoU 追踪和匈牙利算法的区别？**
A：IoU 贪心是局部最优（快，适合高帧率少目标）；匈牙利算法求全局最优匹配（O(n³)，目标多时更公平）。进阶可加 Kalman 预测、ReID 外观特征。

**Q9：你们录像为什么存裸流不存 MP4？**
A：裸流掉电只丢局部，MP4 掉电 moov 头损坏整个文件报废；板端资源有限，裸流+参数集注入即可用 ffmpeg 离线转封装。

**Q10：单生产者单消费者队列为什么可以无锁？——本项目用了锁，但可以答扩展**：A：单写单读可以用环形数组+原子索引实现无锁（但本项目为简单可靠用了 mutex+condvar，队列操作纳秒级不构成瓶颈）。

## 18. 两级检测流水线：VLM 跌倒复核与分级策略

### 18.1 为什么需要两级检测（面试核心问题）

单级方案的问题：YOLO pose 是**感知级**模型——高召回低语义。它只能回答"几何上像不像跌倒"（躯干角度/宽高比/朝向），回答不了"画面里发生了什么"。于是坐沙发、蹲下捡物、换灯泡等姿态都会产生候选。

两级方案：**感知级负责召回、语义级负责确认**，与工业界"粗筛+精筛"完全同构：
```
YOLO pose 高召回候选(低时延,不追求精确)
  → 追踪器 5 连续帧确认 + 15s 冷却(时间维过滤)
  → 现场图(RGB 绘图帧)交给板端 Qwen3-VL-2B
  → VLM 看图回答"结果:是/否/不确定 + 原因"(vision 编码 ~2s + 短答复 ~1.5s)
  → 三级分级报警(urgent/attention/cleared)
```

### 18.2 分级策略与安全语义（宁报勿漏）

| verdict | 含义 | 动作 |
|---|---|---|
| 1 | 真跌倒 | `severity:"urgent"`，证据(图/预录录像)随报 |
| 2 | 无法确认(超时/VLM 失败/解析失败) | `severity:"attention"` 直报（默认 confirm_fallback=alarm） |
| 0 | VLM 明确排除 | 仍发 `severity:"cleared"` 低打扰通知（双保险：监护人可见"已复核排除"） |

三条安全设计（面试可展开）：
1. **证据先行**：图/预录视频/DB 在复核**之前**落盘——复核链路再慢/再失败也不丢证据。
2. **超时宁报勿漏**：复核超时绝不"吞报警"，按未确认直报；解析失败一律归 verdict=2——绝不因解析 bug 把真跌倒误判成"排除"。
3. **排除仍通知**：VLM 若漏判（真跌倒被排除），监护人仍收到 cleared 消息可人工介入。

### 18.3 跌倒静默报警的产品语义决策

复核后**本地不播语音安慰**。理由：① 报警接收方是监护人，跌倒者可能昏迷，语音安慰无救助价值且干扰现场；② 复核后不再追加 LLM 生成+播放，报警更早发出、NPU 不被二次占用；③ 语音通道语义上只服务老人**主动发起**的交互（唤醒对话/求救词），被动检测走静默通道；④ VLM 误判时设备出声会让老人莫名其妙。保留：跌倒发生时若正在播报，复核仍句间掐断（抢占优先级不变）；"求救词"（老人喊救命）的语音回应链路不变。

### 18.4 结构化结论解析（容错设计）

prompt 强制两行输出：`结果:是|否|不确定` + `原因:≤20字`。解析器 parseVerdict（纯文本 C++11，无正则依赖）：
1. 去模板 token（`<|im_end|>` 等）
2. 逐行找"结果:"（兼容中/英文冒号与空格分隔）
3. 分类：无法/未知/不确定→2；不→0（不是/不算）；是→1；否/没→0
4. 无标记行时兜底全文扫描（不确定→2 优先）
5. **全部失败 → 2**（宁报勿漏原则在解析层兜底）

### 18.5 延迟预算（候选→报警 ≤5s 目标）

AI 确认 0.35s + 绘图帧到事件队列 0.05s + 编码/存图 0.3s + 复核请求唤醒 ≤0.6s + vision 448×448 ~2s + 短答复 ~1.5s + MQTT QoS1 ACK ≤1s ≈ **3.5~5.5s**（无抢占；实测数字见验收清单）。

## 19. 单 NPU 多任务资源仲裁与抢占

### 19.1 问题背景

一颗 NPU 上跑四类业务：跌倒复核（VLM+vision）、语音对话（VLM 生成+TTS 合成）、周期巡检（VLM+vision）、远程问答（VLM+vision）。VLM 推理是同步阻塞调用（rkllm_run），且**只能单线程串行**——并发调用同一 LLM handle 是未定义行为。

### 19.2 设计：单执行线程 + 优先级队列

核心决策：所有 VLM 调用收敛到唯一的 chat_llm 线程（红线：VlmEngine 全部调用只发生在此线程，无锁），业务用**优先级**区分：

| 任务 | 优先级 | 抢占规则 | 超时/失败策略 |
|---|---|---|---|
| 跌倒复核 | 1 最高 | 语音生成中→`rkllm_abort`；播放中→句间丢句；远程/巡检→任务结束即打断 | event_proc `future.wait_for(5s)` 超时→按未确认直报 |
| 唤醒/语音段落 | 2 | 不可打断复核 | 现行为不变 |
| 远程命令 | 3 | 无 | 排队；断连丢包记日志 |
| 状态巡检 | 4 最低 | 任何高优先级到达即中止本轮 | 跳过本周期；Persons=0 零调用 |

### 19.3 抢占机制细节（面试可画时序图）

**生成中打断**：event_proc 线程调 `vlm_.cancelRun()`——内部 `rkllm_is_running()` 确认有 run 在跑后 `rkllm_abort(llm_)`（SDK 官方提供的跨线程打断 API；VLM 红线唯一例外）。rkllm_run 以非零返回 + abort_requested 标记 ⇒ 判定为"被打断"。**这是实测项**：若 abort 并发安全异常，回退方案是去掉 cancelRun 一行，靠 event_proc 5s 超时兜底（功能仍完整，最坏延迟 +3~4s）。

**播放中打断**（句级丢句）：复核请求入队时置 `preempt_voice_` 原子位 → tts_play/tts_synth 工作线程在句边界检查，丢弃未开播/未合成句子；正在播放的句子 ≤3s 自然播完即静默。复核跑在 chat 线程（NPU），播报跑在 play 线程（ALSA）——**资源不冲突，复核与播报收尾可并行**，报警不被拖慢。

**等待中打断**：AWAIT_QUERY 状态执行复核，完成后恢复 AWAIT_QUERY 并重置计时（不打断"已建立对话"的体验）。

**跨轮状态竞争防护**：`round_active_` + resetRound 先等上一轮收尾（≤3s 超时强制重置），防旧 play 线程的 finishRound 污染新轮标志位。

### 19.4 巡检的"软实时"调度

巡检不做独立线程：调度器+执行器都是 chat_llm loop 本身（wait 超时 500ms 粒度醒来检查）。执行条件全满足才跑：status_enable && IDLE && 有人 && 距上次对话 ≥10s && urgent 空。设计收益：① 巡检与复核/对话共用 VLM 天然串行，零新线程零新锁；② "仅 IDLE+有人"窗口保证不抢语音轮 NPU；③ 无人时每帧仅一次原子读，零 VLM 调用。

## 20. FrameProvider 按需快照通道

### 20.1 问题

巡检/远程快照/远程问答都要"当前画面一帧"。朴素方案：采集线程每帧 cv::cvtColor(RGB→BGR)+clone 存全局槽——30fps 全量转换+拷贝约 60-90ms/s CPU，不可接受（采集线程是 30fps 实时链路）。

### 20.2 设计：请求驱动的单槽快照

```
采集线程 offer(mat):  want_==false 直接早退(零开销) —— 平时 30fps 全走这条
                      want_==true → cvtColor(RGB→BGR, 输出即独立缓冲) → 落槽 + seq_++
AI 线程 reportPersons(n): 原子写(巡检"有人"判定)
chat 线程 request(timeout): 置 want_ → 等 seq_ 变化(≤1 帧 ~33ms) → clone 返回 → 清 want_
```

要点：
1. **按需转换**：转换/拷贝只在"有请求在等"的那 1-2 帧发生。
2. **生命周期安全**：cvtColor 输出是独立新缓冲，绝不把采集缓冲的 Mat 视图传出线程（下一帧就被 RGA 覆盖）；槽位 Mat 只在采集线程写，request 返回 clone。
3. **单请求者模型**：巡检/远程命令都在 chat 线程执行，天然串行，无多请求竞争。
4. **无人帧支持**：采集主循环"有人才绘图"路径之外增加 wanted() 检测——远程快照要拍"空房间"图时走一次 RGA 旋转+转换投递（同样只在被请求时）。

### 20.3 线程安全分析（面试可展开）

- offer/request 之间仅一把锁保护槽位与 seq_（cvtColor 也在锁内，~几 ms 可接受）
- 跨线程只传递 clone 后的 Mat（OpenCV Mat 引用计数只管内存生命周期，不管跨线程并发写——本项目用"clone 隔离"策略规避）
- 退出顺序：TLmain 先 join 编码线程（此后无 offer/report），再 stop chat 线程——request 超时自然返回空，无悬挂

## 21. 远程操控协议与安全（公网 MQTT）

### 21.1 Topic 设计（多设备隔离）

| 方向 | topic | retained | 说明 |
|---|---|---|---|
| 上行报警 | `home/fall` | 是 | 现报文 + severity/vlm_confirm 可选字段 |
| 上行状态摘要 | `home/{device_id}/timeline` | 否 | 周期巡检 |
| 上行应答 | `home/{device_id}/resp` | 否 | 命令应答，req_id 关联 |
| 上行设备状态 | `home/{device_id}/state` | 是 | online/offline，后来者也能读到 |
| 下行命令 | `home/{device_id}/cmd` | 否 | 设备 subscribe 的唯一下行点 |

`{device_id}` 占位符加载时替换为 `[event] device_id`——多设备共用一份配置模板。

### 21.2 协议语义

- **snapshot**：FrameProvider 抓帧（无人也可拍）→ 长边 320 缩略 → base64 回传
- **chat**：抓帧 → `<image>用户文本` 交 VLM → 回文本。**默认不本地播报**（remote_voice=0：避免远程回复突然在老人房间出声）
- **timeline/events**：queryRecent 只读查库（读也走 EventManager worker——SQLite 单连接不做并发读写）
- **ping**：在线状态 + 画面人数
- 错误码：401 未授权 / 404 取帧失败 / 503 VLM 忙 / 400 参数错
- **忙时的命令不会丢**：语音轮/巡检/复核进行中到达的远程命令只是排队（`ev_queue_`，上限 32），
  当前处理函数结束后按序执行。主循环里那个 `// BUSY：丢弃一切输入` 分支**不可达**——
  所有置 BUSY 的处理函数都在返回前恢复状态，且 `state_` 只由 chat 线程读写
  （2026-09-13 据此删掉了一段误加的"回 503"死代码，详见开发日志）

### 21.2.1 客户端形态（2026-09-13）

两个客户端走**同一套协议**，可共存：

| 客户端 | 传输 | 用途 |
|---|---|---|
| `client/remote_demo/remote_demo.py` | MQTT over TCP（paho） | 命令行调试工具 |
| `client/web_demo/index.html` | MQTT over WebSocket（mqtt.js） | 手机/电脑浏览器操控面板，**快照直接渲染成图** |

网页客户端用 `ws://` 连 broker 的 8083 端口（mosquitto 的 `protocol websockets`），
因此页面本身必须用 `http://` 打开——https 页面会被浏览器拦截 ws 连接（混合内容）。

### 21.2.2 远程实时视频：按需推流（2026-09-13 验收）

**为什么 RTSP 不能直接远程看**：① 浏览器原生不支持 RTSP；② RTSP 是"客户端主动拉"，
板端在家庭 NAT 后没有公网 IP，外网够不到 8554。而 MQTT 能通是因为**双方都主动外连 broker**。

**架构（对齐工业模型）**：

```
手机网页点「看视频」
  → MQTT start_stream（复用命令通道，带 auth）
  → 板端 fork/exec ffmpeg：拉本地 rtsp://127.0.0.1:8554/h264（子码流带AI框）
        -c copy 零转码 → 推 RTMP 到云端 MediaMTX（1935）
  → MediaMTX 转 HLS（8888）→ 网页 HLS.js 播放（延迟 3~5s，多端可同时看）
点「关流」→ kill ffmpeg（SIGTERM 宽限 1s → SIGKILL）+ waitpid 收僵尸
```

**工业对应**（面试可讲）：
- 信令触发开流 = 消费级监控（萤石/小米）的信令架构：设备 7×24 连云，App 要看了才下发推流
- 设备**推**流到平台 = GB28181 国标推流模型 + 直播行业 RTMP 推流十年标准
- 差异：工业用 P2P 打洞省云带宽、延迟 1~3s；本项目单路演示走云转发、HLS 3~5s

**工程要点**：
- 源可配 `stream_src_url`：h264=子码流（H.264，全平台浏览器可播）；h265=主码流
  （H.265 专利问题，**仅 iPhone Safari 原生可播**，Android/PC Chrome 黑屏）
- ffmpeg 是**项目第一个 fork/exec 子进程**：stderr 落 `/tmp/stream_push.log`；
  起进程在 chat 线程就地做（毫秒级），唯一同步等待是 stop 时的 waitpid 轮询（≤1s）
- 网页时序坑：板端推流启动有 2~3s 空窗（RTSP 握手+RTMP 连接+首分片），
  网页收到应答立刻拉 m3u8 必 404 → 延迟 3s 加载 + manifestLoadError 重试 6 次
- 裁剪项与补法见开发日志（自动停流/退出清理/推流鉴权）

### 21.3 接收链路的线程模型（红线）

paho 消息回调(msgArrived)在 `MQTTClient_receive` 的调用线程内同步触发。规则：**回调线程只入队**——回调内 copy payload → 调 `ChatEngine::onRemoteCommand()`（快速入队）→ 解析/执行全部在 chat 线程。绝不在回调里碰 VLM/DB。

### 21.4 重连的正确姿势（易错点）

paho 的 callbacks 与 subscription 都绑定 client 句柄：连接断开重建句柄后，**必须重新 setCallbacks + 重新 subscribe**（本项目前几版在此踩过坑，订阅失效导致命令收不到）。

### 21.5 安全（面试可讲的亮点）

1. **认证**：`[vlm_pipeline] remote_token` 非空时校验命令的 auth 字段——**不等长比较**（逐字节 XOR 累积，常数时间）防时序侧信道；失败仅回 401 并记日志。
2. **Topic 隔离**：每设备独立 cmd/resp topic；生产部署建议 broker ACL（EMQX/mosquitto 可配用户名→topic 权限表）。
3. **隐私红线**：快照是实时画面回传——公开 broker 不设 token 等于任何人可触发摄像头拍照，配置注释明确警告。
4. 公网通道（2026-09-13 落地）：云服务器自建 **mosquitto**（选型理由见开发日志：
   EMQX 5 的 REST API 文档不完整、ACL 端点有版本差异、资源占用大），**三层访问控制**——
   ① broker 账号密码（谁能连）② mosquitto ACL（能订阅哪些 topic）③ app 层 `remote_token`（能否执行命令）。
   一键部署脚本 `server/tools/setup_public_broker.sh`，步骤见 `docs/公网MQTT部署清单.md`。
5. **为什么不用 TLS**（面试可能被问，要能答）：
   - 现成的 `libpaho-mqtt3cs.so` 是用**已弃用的 RK3568 工具链**编的，依赖 OpenSSL **1.1**；
     而 RK3588 工具链与板端都只有 OpenSSL **3** → 直接用会缺 `libssl.so.1.1`
   - 要用 TLS 必须用 RK3588 sysroot（OpenSSL 3）重编 paho（`-DPAHO_WITH_SSL=TRUE`）+ 加 `MQTTClient_SSLOptions` + 证书分发
   - 本项目为个人演示场景，明确权衡后**不做**：MQTT 口令与 base64 现场图在公网明文传输，靠上述三层访问控制兜底
   - ⚠️ 这意味着**密码强度就是唯一屏障**——`mqtt1/123456` 这类默认值绝不能带上公网

## 22. 实测性能数据（2026-09-10 板端实测，简历数字来源）

> 面试注意：本章每个数字都要能答出**测量方法**（日志行/工具/命令），
> 被追问"数字怎么来的"时直接指到对应日志格式。

### 22.1 稳态指标（无 VLM 任务时）

**CPU 占用（watchload 实测，2026-09-10 用户贴图数据）**：
- 平时（双码流 30fps + YOLO 15fps 常驻）：8 核平均 ≈2.2%；小核(CPU1-4) 0~1.3%，大核(CPU5-8) 4.7~8.6%
- VLM 任务期间（vision+生成，两次实测）：8 核平均 16~22%，大核峰值 37~40%；
  小核 12~17%（ASR+采集调度），大核 22~37%（VLM 预处理/调度）；温升 4~5.5°C
- 结论：视频/检测链路 CPU 占用极低（编码走 MPP 硬件、旋转缩放走 RGA 硬件），
  只有 VLM 的预处理/调度吃大核——这正是"硬件加速分层"设计的实测证据

| 指标 | 实测值 | 来源 |
|---|---|---|
| 主码流 | 30fps，编码延迟 LatAvg 10~13ms（4K 采集→RGA 缩放→1080p H.265） | `[MAIN]` 统计行 |
| 子码流 | 30fps，编码延迟 ~10ms（640x480 H.264 带 AI 框） | `[SUB]` 统计行 |
| YOLO 推理 | 15fps（每 2 帧取 1 帧 AI），Inf p50=23ms p95=29ms | `[SUB]` 统计行 |
| 检测滞后 | DetectLag 10~55ms（AI 出结果到绘图的时效） | `[SUB]` 统计行 |
| NPU 负载 | Core0/1/2 = 2/0/34%（YOLO 单模型） | watchload `/sys/kernel/debug/rknpu/load` |
| 温度/频率 | 37°C；NPU 1.0GHz、CPU 2.26GHz 满频（定频脚本） | watchload + devfreq/cpufreq |
| 内存 | TLServer RSS 3.3G（模型 ~2G 文件页 + ~1G 匿名缓冲）；系统 used 1.25G/15.57G；CMA 总量 ~0.28G | watchload + /proc/meminfo |

### 22.2 VLM 任务期间（单 NPU 仲裁的代价与边界）

一次完整巡检（vision 编码 3182ms + 生成 3717ms，总 6.9s）期间：

| 时刻 | YOLO 帧率 | Inf 均值 | AIwait | DetectLag |
|---|---|---|---|---|
| 巡检前 | 15~16fps | 41ms | 0.2ms | 10ms |
| vision 编码中 | 15→11→5fps | 61→194ms | 10→372ms | 133ms |
| 生成中（最差） | **3~5fps** | 383ms | **413ms** | 263ms |
| 结束后 1s | 14fps | 57ms | 112ms | 48ms |
| 结束后 2s | 15fps | 22.9ms | 0ms | 48ms |

关键结论（面试直接讲）：
1. **主码流全程 30fps、延迟零波动**——编码走 MPP/RGA 独立硬件，与 NPU 争抢无耦合。
2. **降帧是排队不是推理变慢**——p50 全程恒 23ms，变的是 AIwait（0→413ms）与
   DetectLag（峰值 263ms）。这就是 [SUB] 行引入 AIwait/DetectLag 两个指标的原因：
   把"推理慢"和"排队长"分开，诊断才有依据。
3. **2 秒恢复**：VLM 任务结束 2s 内 AI 回到 15fps/22.9ms。
4. **优先级保障**：巡检是低优先级任务；真跌倒时 urgent 复核会 rkllm_abort 抢占，
   所以"巡检期间跌倒"的代价最多是 ~0.4s 检测滞后，不会漏报。

### 22.3 VLM 任务耗时分布

| 环节 | 实测 | 说明 |
|---|---|---|
| vision 图像编码 | ~3.2s（巡检场景，与 YOLO 争抢） | 3 核 NPU；日志注释"并发争抢会拉长" |
| 多模态生成 | ~3.7s | 短句摘要 |
| 跌倒复核全链路 | 3.5~7s（空载/争抢） | 超时 12s 兜底直报 attention |
| 巡检全链路 | 6.9s（30s 周期内占比 23%） | 含抓帧+落盘+编码+生成 |

### 22.4 资源利用与稳定性观察

- **NPU**：VLM 任务时三核 97/40/75%（单模型 YOLO 时 0/0/34%）——rkllm 多核并行生效。
- **温度**：37.0°C → 40.7°C，VLM 全速推理温升仅 ~4°C，距 75°C 降频红线余量大。
- **内存语义**（面试考点）：TLServer RSS 3.3G 但系统 used 仅 1.25G——模型权重是
  **文件映射页**，Linux 计入 page cache 不计入 used；空闲后内核回收部分文件页，
  RSS 降至 2.5G（回收不是泄漏，泄漏只涨不降）。
- **CMA**：总量 ~0.28G、使用 0.07G，TLServer 全量 CMA 缓冲方案在板端 CMA 配置下无压力。

### 22.5 尚未量化的指标（诚实清单，面试被问就说"没专门测过"）

**零拷贝收益对照实验（membench 工具，/tmp/membench，交叉编译自 /tmp/membench/membench.c）**：
- 方法一（membench 带宽基准，★L3 逐出修正：每次测量前搬 16MB 垃圾挤掉缓存，
  否则小缓冲全程命中 4MB L3 测出 26GB/s 假象）→ 单次全帧拷贝耗时 × 非零拷贝
  管线典型拷贝次数(3 次: 采集→AI 输入 / AI 结果→绘图 / 绘图→编码) = 每帧拷贝成本
- **实测（2026-09-11，冷拷贝带宽 9.3~9.6GB/s）**：
  | 帧尺寸 | 单次拷贝 | 3 次拷贝/帧 | 30fps 流量 | 占1核 |
  |---|---|---|---|---|
  | 640x480 NV12 (460KB) | 0.048ms | ~0.15ms | 42MB/s | ~0.4% |
  | 1920x1080 NV12 (3MB) | 0.325ms | ~1ms | 280MB/s | ~3% |
  | 3840x2160 NV12 (12.4MB) | 1.344ms | **~4.0ms(帧预算33ms的12%)** | **1.1GB/s** | **~12%** |
  → 结论：零拷贝收益大头在 4K 主码流（省 ~4ms/帧 + 1.1GB/s 带宽 + 单核 12%）；
  子码流毫秒数不大，其价值在"无 CPU 介入即无缓存一致性问题"
- **方法二（A/B 对照实测 2026-09-11，config extra_copies 开关模拟插入全帧拷贝）**：
  主码流 LatAvg 0 拷贝 10.8ms → 1 拷贝 14.2ms(+3.4ms，含临时缓冲冷启动缺页)→
  3 拷贝 17.9ms(**+7.1ms，+66%；稳态单拷贝 ~1.85ms，与 membench 1.34ms 互相印证**)；
  子码流单独 A/B(仅开子码流拷贝)：3 拷贝 4.2~4.3ms vs 同会话 0 拷贝 6.4~9.4ms——
  **拷贝不可能是负成本;代码审查确认实验装置无 bug(拷贝在 LatAvg 窗口内、
  frame_size 正确)。真实机制:单 RGA 引擎排队相位——主码流每帧 4K→1080p 缩放
  (2~4ms 大任务)与子码流的 3 个 RGA 小任务共用一颗 RGA,基线轮子码流请求频繁
  排在缩放后面等 2~5ms(LatMax 13ms),拷贝的 0.15ms 微延迟恰好把相位错开
  (LatMax 5~6ms,几乎不排队);两路同开拷贝时主码流相位被挪,子码流撞车概率
  再变(5.3ms)——四轮数据统一闭合。结论:子码流绝对延迟由 RGA 排队相位主导
  (4~9ms),0.15ms 拷贝成本无法用 A/B 隔离,可信来源 membench(0.048ms×3);
  主码流每帧仅一个 RGA 大任务、无相位运气问题,A/B 数据(+66%)过硬。
  ★副产品发现:双码流共用一个 RGA 引擎的排队是系统真实瓶颈(仅靠读代码无法
  发现,对照实验暴露)。**决定性验证(主码流 enable=0 开关,四象限矩阵)**:
  关主码流后 0 拷贝 3.8~4.4ms 极稳(LatMax 5ms)、3 拷贝 4.0~4.4ms——子码流
  真实基线 ≈4.1ms、拷贝成本 0.1~0.2ms 与 membench 一致;连 NPU 推理 p95 都从
  78~107ms 降到 23~26ms(主码流的 DDR 流量同时拖累 NPU 尾延迟)
  → **简历口径：零拷贝每帧省 ~7ms(3 拷贝口径,A/B 实测);子码流收益 <0.2ms
  (带宽基准),收益大头在 4K 主码流**
- 语音全链路（[Voice] 自动打点实测 2026-09-11）：**说话结束→首句播报 5.5s（纯文本
  问答）/ 9.5s（带图视觉轮）**；构成 = 静音判停 2s + 识别尾延迟 ~1.5s + VLM 生成 ~2s
  + 首句合成 ~0.3s；带图轮多 vision 编码 ~3.2s。非流式对照：TTS 整段合成首句 14s→3s
  已是流式化的收益；ASR 非流式对照组 = 整句时长 + 整句解码(时长×RTF)，长句省 5-9s

### 23.4 上下文记忆(面试问题"有上下文记忆吗"的标准答案)

- **语音纯文本多轮:有记忆**。rkllm_run keep_history=1,KV cache 保留会话历史,
  每轮只喂新增 user 输入;连续对话(15s 无说话才退出)内上下文连贯(实测西罗/梅西
  追问轮引用前文)。超时退出时 clearHistory(保留系统人设段)等价新会话
- **无记忆/隔离的场景(每次调用前 clearHistory)**:视觉轮(防同会话第二张图触发
  PAD token 洪泛)、跌倒复核、巡检、远程问答、求救判定——业务间 KV 隔离是设计,
  防止"陪伴人设的记忆"污染"复核判断"的客观性
- 远程问答另有**人设切换**:setSystemPrompt(remote_chat_prompt) 毫秒级换 system 段,
  结束恢复陪伴人设
