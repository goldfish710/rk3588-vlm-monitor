### 数据流速记
```
主码流: /dev/video0 (2592x1944) → MPP H.265 → SharedQueue → live555 RTSP /h265
        └→ VideoRecorder（循环录像切片 + 事件预录环形缓冲 + 事件录像）
子码流: /dev/video1 (640x480) → [抽帧→RGA旋转270°→RKNN零拷贝推理→跌倒/坐姿分类→追踪]
        → RGA 绘图（框/骨架/姿态标签）→ 写回 → MPP H.264 → RTSP /h264
跌倒确认 → 事件线程: 存图(JPEG) + SQLite 落库 + MQTT 报警(带图 base64) + 主码流事件录像
```

### 关键线程（start_encode_h264 内）
- `h264_ai_enc` 主采集编码线程（含 RGA 绘图管线）
- `h264_ai` AI 推理线程（letterbox→rknn_run→post_process→classify_pose→PersonTracker）
- `event_proc` 事件线程（存图→DB→MQTT）
- `h265_enc` 主码流编码线程、`recorder` 录像线程、`mqtt` MQTT 线程、`monitor` 健康监控（编码线程死则 abort 重启）

### [2026-08-17] VLC 无声排查：采样率 16k→44.1k + 单声道取 ch0

**现象**：用户 VLC 播放本地 MP4 和拉 RTSP 主码流都没有声音（其他播放器打不开文件）。

**排查结论**（链路逐段验证，全部正常）：
- 板端 MP4 音频内容有真实声音（volumedetect mean -17.9dB）
- PC ffmpeg 完整解码 58.3s 音频（93 万样本）
- MP4 结构标准（时间戳/双轨/时长对齐）
- 板端 RTSP 回环 ffprobe 双流 + ffplay 播放正常
→ 录制/编码/封装/推流链路无问题，问题在 VLC 兼容性（16kHz 低采样率在部分 VLC 版本下音频轨不发声）与"其他播放器"是 Windows 缺 HEVC 解码器扩展（行业性问题）。

**修复（已上板验证）**：
1. **采样率 16kHz → 44.1kHz**（默认值 config.h）：44.1k 是所有播放器兼容性最好的采样率；用户 arecord 44100 实测硬件路径正常。ASC 自动变为 0x1208（freqIdx=4）
2. **单声道取 ch0**（新配置 audio_mono_source=1，默认）：实测麦克风只接声道 0（ch1 基本底噪），(L+R)/2 降混白损 6dB 信噪比。AacEncoder 支持 0=降混/1=左/2=右
3. **修复隐藏 bug**：Mp4Muxer 音频轨 timescale 写死 16000，VideoRecorder 两处 openNewSliceFile/processEventMp4Start 漏传 aac_sample_rate_——16k 时恰好一致未暴露，换采样率必崩。已补 `mc.audio_timescale = aac_sample_rate_`

### [2026-08-17] 嗡嗡声根因：30Hz 摄像头帧时钟干扰族（频谱分析法定位）

3. 验证：150Hz 以下全部压到百万级以下（原几千万）；残余 300/360Hz 高次谐波**故意不陷**（在语音 F1 共振峰区，陷了伤语音清晰度）——听感上是"嘶"声，被语音掩蔽

### [2026-08-18 凌晨] zipformer 流式语音识别（呼救关键词 → MQTT help_call）

**背景**：用户选定"只做 zipformer ASR"路线（官方 rknn_model_zoo 支持，中英双语流式，RK3568 实测 RTF 0.116）。功能：连续识别老人说话 → 本地匹配呼救关键词（救命/来人/救救我/帮帮我，可配置）→ `mqtt_push_event(event="help_call")`。识别全文永不上报（隐私），仅 debug_text_log 时打日志。

**探索发现的两个关键约束**（官方 demo 一次性处理 wav，流式集成必须解决）：
1. **kaldi-native-fbank 不内置重采样**（AcceptWaveform 的 sampling_rate 参数仅用于断言匹配，.a 里无 resampler 符号）→ 44.1k→16k 自写线性插值重采样（流式相位状态 Resampler 类）
2. **重叠 hop 水位必然增长**：每 chunk 消费 103 帧只前进 96 帧（重叠 7 帧），音频 100 帧/s 到达 → 水位 ~6.8 帧/s 永续增长 → 水位策略：ready-processed ≥ 103+96 时跳一轮排空（丢 0.96s，~每 15s 一次，限速打日志）

**架构**：AudioCapture 采集线程 addSink 回调内降混（audio_mono_source 语义）+入有界队列（2048×50ms，满丢最旧）→ ASR 线程（nice=10 低优先级）出队 → 重采样 → fbank（80 维 mel/10ms 帧移/16k）→ 凑够 103 帧跑 chunk → encoder（36 入/36 出，输出 1-35 状态回填输入，4D 状态 NCHW→NHWC）→ 贪心（24 帧×joiner+逐 token decoder）→ 文本滚动缓冲（▁→空格拼接去空格，最近 10s）→ 关键词子串匹配（BPE 下"救命"会被切成"救"+"命"两 token）→ 冷却 30s → 事件回调。静音门控：AudioCapture::silent() 为真时丢弃 PCM 不喂 fbank。

**新增文件**：server/cpp/asr_thread.h/.cpp（AsrEngine 类，~700 行，移植官方 zipformer.cc/process.cc + 增量流式化）；server/cpp/3rdparty/kaldi_native_fbank/（预编译 .a 202KB + 10 头文件，从 rknn_model_zoo 拷贝）。修改：config.h/cpp（[asr] 节 8 键+3 运行时字段）、TLmain.cpp（接线+清理顺序）、CMakeLists.txt（SOURCES/include/link 四处）。

**踩坑**：
- OnlineFbank 是 `using` 别名非 class，无法前置声明 → 头文件直接 include online-feature.h
- **kaldi 预编译库未开 -fPIC + buildroot 工具链默认 PIE** → 链接报 R_AARCH64_ADR_PREL_PG_HI21 重定位错误 → CMakeLists 加 `set(CMAKE_EXE_LINKER_FLAGS "-no-pie")`（板端常驻进程不需要 PIE）

**模型**：3 onnx 网盘下载（encoder 78MB/decoder 13.9MB/joiner 12.8MB）→ conda python3.8-tk2-2.2 官方 convert.py 转 fp16 rknn（111MB/8MB/6.5MB）→ 板端 /userdata/tlserver/model/ + vocab.txt(6257 词 BPE)。

**验证结果**：

### [2026-08-20] 严重 bug 修复:播放→采集流损坏链(语音识别偶发失效+播放结尾截断)

**用户实测现象**:①运行中偶尔语音识别完全失效(一开始正常,某次播放后彻底无识别);②TTS 播放结尾"像被突然中断"。

**日志证据链**:播放 9.08s 长回复 → 播放开始 1s 内 `[AudioCapture] xrun(1)` → 播放结束后 `读取失败: Input/output error (连续1/2/3...)` 每 ~10s 一次 → 之后无任何 ASR 输出。

**根因**:hw:0,0 上长音频播放与采集并发 → 采集 xrun → snd_pcm_recover 对 -EIO 无效,采集流进入死循环(readi 阻塞 10s 返回错误);而采集的 recover 动作重配硬件时钟又**反过来截断正在播放的音频**——两个现象同一根因。

**修复(三件套)**:
1. **播放期间暂停采集**(AudioCapture::pauseCapture/resumeCapture:drop/prepare;ChatEngine 的 play_state_cb 扩展,播放时同时 suppress ASR+暂停采集)——播放时录的本就是喇叭回声,暂停双赢,录像音轨播放期间静音(可接受,注释说明)
2. **采集流自愈**:连续失败 ≥3 次 → 完整重启设备(drop/close/openDevice/set_params/start),取代原来"失败 30 次退出"——流被任何外部操作损坏后 ~30s 内自动恢复
3. 暂停期间 readi 被 drop 打断属预期,失败分支先检查 paused_ 静默等待,不进失败计数

**全项目严重 bug 审查结论**(用户要求):除本 bug 外未发现其他严重问题。已知的轻度问题(录在"已知问题"区)均不影响主链路,按用户指示不动。

**第二轮实测暴露更深层规律(用户日志分析)**:
- 自愈机制验证有效:失败 3 次 → 重启设备 → 采集恢复、识别恢复(18:33:50→18:33:54)
- 但**每次播放结束后 ~13-16s,采集流必然再次 -EIO**(播放 3.61s→16s 后失败;播放 3.11s→16s 后失败)——prepare 恢复的采集流带着被播放破坏的 codec 时钟跑,漂移累积后损坏
- 修复:**resumeCapture 改为请求完整重启**(close+openDevice 重置时钟),由采集线程自己执行(need_restart_ 标志+drop 打断 readi,避免跨线程 close 与 readi 竞争)——播放后的失败从根上消除,失败自愈仅作兜底
- 教训:**"恢复"和"重启"在硬件层是两回事**——prepare 恢复的是软件流状态,close+open 才重置硬件时钟;嵌入式音频问题要区分这两层

**第三轮实测(用户):重启机制运行良好(每轮播放后自动重启,连续多轮零失败零空窗)。用户新反馈"播放结尾像被突然中断"**:
- 数据层验证:PC 直接调火山合成同句,尾部完整(200ms 静音衰减,emoji 不截断)
- 播放层验证:板端 aplay 播同一 wav + mic 录音能量分析,播放完整(尾部正常衰减)
- 结论:非截断,是**句尾静音太短(~200ms)导致"戛然而止"听感**
- 修复:AudioPlayback 播放数据尾部追加 400ms 静音缓冲(呼吸感+兜底 drain 截尾)
- 方法论:**"听感 bug"先分三层验证:数据层(PC 直连 API 对比)→ 播放层(aplay+录音能量分析)→ 代码层**,每层用数据说话

**延迟调优(用户反馈"播放完还要等一会才能说话")**:等待主因不是重启(几十 ms),而是**播放尾 2s 回声门控**——该门控是"采集开启"时代的回声抑制设计,现在播放期间采集已暂停(无回声进入),2s 纯属拖延 → 删除,播放结束立即恢复采集。剩余延迟 = ASR 固有(攒帧 1.03s + 判段 1s ≈ 2s),不可消除。关于"消除重启":理论上播放流常开复用(不 close)可避免时钟扰动,但需实测验证稳定性,当前重启方案已实测可靠,不冒险。

### [2026-08-20 晚] 长稳测试:段错误定位修复 + 内存增长待实测

**用户长稳测试(28min)发现:①程序段错误停止;②系统 Used 580→635MB 疑似泄漏;③板子 USB 掉线(重连后恢复)**。

- 修复:所有 pcm 操作归采集线程——pause 只置 paused_ 标志(采集线程 readi 返回后自行挂起,滞后 ≤50ms);resume 只置 need_restart_(轮询中完整重启);shutdown 的 drop 保留(退出路径,历史验证)

**内存增长(定位过程两轮,最终修复)**:
- 板端 mem_watch.sh 实测:VmRSS 每 2 分钟恒定 +4216KB(35KB/s)。**第一轮误判**:以为是"每 2 秒重建 fbank 泄漏 70KB"——修复(跳帧替代重建)后曲线不变 → 假设被数据否定
- **第二轮正确归因**:35KB/s 是**平均速率**不是周期——真凶是 **fbank 内部帧从未被删除**:"跳帧"只前移消费指针,RecyclingVector 里的历史帧(静音喂数据 100 帧/s × 320B = 32KB/s)无限积累
- 板端小测试(交叉编译 test_pop,链 kaldi .a)确认 Pop 语义:NumFramesReady 是绝对计数不变;GetFrame(未删帧)有效;已删帧真正释放内存(访问抛 out_of_range)
- 修复:每次喂数据后 `fbank_->Pop(processed - 200 - 103)` 回收已消费旧帧(保留余量);静音跳帧前移 processed 后同样被回收 → 帧数有界
- **教训:恒定步进泄漏曲线只给"平均速率";两次假设都是"速率吻合"但机制不同——第一版是周期推断错误,第二版才是真内存语义问题。修复后必须用数据验证,而不是"应该好了"**

**修复验证+收尾(08-22)**:
- 用户实测 74 分钟:VmRSS 204→214→203MB,曲线完全拉平(±6MB 波动,后期下降)——**泄漏根治,数据确认**
- Pop 增量修复后不再崩溃(此前"再删 n 帧"语义导致帧被删光+GetFrame 下溢 abort)
