## 故事 1:混合量化事故——为什么我的模型"看着对,实际全错"

**对应简历亮点**:混合量化、模型部署

**30 秒版**:我把 yolov8n-pose 量化成 INT8 部署到 NPU,检测框正常但关键点置信度全废了。排查发现是量化对"坐标+置信度混合值域"的张量极不友好——关键点张量里坐标是几十几百、置信度是 0~1,一个 scale 无法同时表示两个量级。最后用官方 hybrid 方案把关键点分支保留 FP16,精度回来了,推理只慢了 8%。

**2 分钟版**:

1. **现象**:INT8 量化后,检测框、类别都对,但 17 个关键点的置信度全部失效(值域错乱),骨架线画不出来
2. **排查路径**:
   - 先怀疑后处理:拿连板诊断脚本 dump 模型原始输出,发现**模型的输出本身就坏了**,不是 C++ 解析错
   - 再怀疑量化参数:输出张量的 scale=3.19——关键点原始值是 0~1,乘 3.19 再转 int8,精度只剩 1/3.19≈0.31 的分辨率,**0~1 的小数全被碾碎**
   - 本质:关键点张量是"坐标(值域数百)+ 置信度(值域 0~1)"混在同一张量,单个 scale 必然顾此失彼
3. **根因**:per-tensor 对称量化对混合值域张量的表达能力不足——这不是我代码的 bug,是量化方案的选型问题
4. **修复**:官方 hybrid quantization——把关键点分支(D-FL 输出到 Concat)从量化图中排除,保留 FP16,其余 INT8。结果:置信度恢复 0~1 正常分布,推理 49.4→45.3ms(反而快了 8%,因为 FP16 分支转换更少)
5. **沉淀**:模型部署三件套——上线前必查"启动日志的输出张量 type/zp/scale + 连板 dump 值域 + 实拍复测"。以及:**量化不是免费的午餐,精度损失集中在"混合值域"张量上**

**可能被追问**:
- Q:"scale 是什么?" A:量化 = 实数 → int8 的线性映射,scale 是步长。per-tensor 一个张量一个 scale,per-channel 一个通道一个
- Q:"为什么 hybrid 反而快?" A:关键点分支保 FP16 后,该分支省掉了量化/反量化节点,net 开销下降——量化节点本身有成本
- Q:"你怎么知道是官方方案的?" A:读 rknn_model_zoo 官方 yolov8_pose 转换脚本,它有 custom_hybrid 参数专门处理这类模型

## 故事 2:自研 HTTPS 客户端的"语义 bug"——板端只能告诉我错了,PC 测试才能告诉我错在哪

**对应简历亮点**:手写 HTTPS/SSE 客户端

**30 秒版**:板端没有 curl,我手写了 400 行 HTTPS 客户端(TCP+OpenSSL+chunked 解析)接 DeepSeek 流式接口。上线后板端一直报"SSE 流未正常结束",但 PC 上 curl 完全正常。我把客户端编译成 PC 测试程序连真实 API,发现响应体只剩最大那个数据块——chunked 读取函数把"读 N 字节增量"实现成了"读到总共 N 字节",小块全被跳过。改一行修好。

**2 分钟版**:

1. **现象**:板端调 DeepSeek 流式接口,每次报"SSE 流未正常结束"(收不到结束标记 `[DONE]`);同请求 PC curl 正常——**同样的服务器、同样的请求,只有我的客户端错**
2. **排查路径**:
   - 板端日志信息量太少(只有"未正常结束"),于是**把客户端源码在 PC 上编译成独立测试程序**,连真实 API,打印响应体
   - 关键发现:响应体大小恰好等于最大 chunk 的大小;chunk 大小序列 562/278/284/284/840/461/0,响应体正好 840 字节——**前面 5 个块全丢了**
   - 锁定函数语义:`readExact(body, n)` 我实现成"读到 body 总共 n 字节",而调用方(chunked 循环)传的是"本块新增 n 字节"。body 已经 562 字节时,"再读 278"的调用直接跳过——小块的判断恒假
3. **根因**:函数语义(增量 vs 目标)与调用方约定不一致——一个词都没写错的 bug
4. **修复**:记录调用前 size,按差值读:
   ```cpp
   size_t start = body.size();
   while (body.size() - start < n) { ... }
   ```
5. **沉淀**:**自研协议客户端必须在 PC 上写独立测试程序、连真实服务对比 curl 验证,再上板**。板端日志只能回答"对不对",PC 测试能回答"错在哪一步"——这套方法后来整个项目的联调都在用

**可能被追问**:
- Q:"chunked 格式是什么?" A:HTTP 分块传输,`<十六进制长度>\r\n<数据>\r\n` 重复,`0\r\n\r\n` 结束——流式接口标配
- Q:"为什么不用 libcurl?" A:板端 buildroot 无 curl 无 CA 证书,交叉编译 libcurl 引入一坨依赖;400 行自研换取零依赖与完全可控的超时
- Q:"SSE 是什么?" A:Server-Sent Events,`data: {...}` 行式推送,`[DONE]` 结束;LLM 流式输出的业界标准

## 故事 3:"播放正常但没声音"——实验矩阵定位硬件约束

**对应简历亮点**:音频链路、板端调试

**30 秒版**:TTS 播报功能做好后,日志显示播放正常但喇叭没声,而且 Ctrl+C 退出瞬间声音突然全出来。我用"aplay 播放 + 板载麦克风录音分析能量"做实验矩阵:采集停止时喇叭有声、采集运行时播放阻塞。定位到 ALSA 的 dmix 软混合与硬件采集并发冲突,改直连硬件后又发现新约束:采集/播放共享时钟(必须同为 44.1kHz)、硬件最少双声道——软件为硬件约束做了三层适配。

**2 分钟版**:

1. **现象**:播放日志正常(`[Playback] 播放 ... 4.84s`),无声;Ctrl+C 退出瞬间,声音突然全出来
2. **排查路径**(不用示波器、不读驱动源码,纯实验):
   - 假设"有声但被阻塞"——设计对照实验:**TLServer 停止时** aplay 播放+mic 录音:峰值 4724,有声 ✓;**TLServer 采集运行时**同样测试:aplay **永久阻塞**
   - 真相:退出时采集先停止 → 阻塞解除 → 积压的音频放出来 = 用户听到的"退出时才播放"
   - 修复方向:播放直连 hw:0,0 绕过 dmix。紧接着连环撞出两条新约束:"Rate doesn't match"(采集锁 44.1k,播放必须 44.1k → 16k TTS 音频要先上采样)、"Channels count non available"(硬件最少 2 声道 → mono 复制双声道)
3. **根因**:ALSA 默认设备(dmix 用户态混合器)与硬件采集并发时 writei 阻塞;RK809 codec 采集/播放共享时钟
4. **沉淀**:①"正常但无声/阻塞"先怀疑设备路由与并发冲突,实验矩阵(开/关 × 设备)比读文档快;②**单独测都好的组件,并发时才暴露约束**——嵌入式里"能用"和"一起用"是两回事
5. 顺带的方法论:用"板载 mic 录音 + 能量分析"做**无人工的客观验证**,把"我听着没声"变成数据

**可能被追问**:
- Q:"dmix 是什么?" A:ALSA 用户态混音插件,让多程序共享声卡,代价是间接层与时钟对齐问题
- Q:"为什么采集锁 44.1k?" A:配置里为 VLC 兼容选了 44.1k(16k 在部分 VLC 不发声),而 RK809 的 capture/playback 共享时钟域

## 故事 4:静音门控吃掉每句话的开头——控制信号的滞后比 bug 更隐蔽

**对应简历亮点**:流式语音识别

**30 秒版**:流式语音识别上线后,短句几乎全丢、长句只丢开头。排查发现是我的"静音省算力"优化:静音判定每秒才更新一次,开口瞬间它还是"静音"状态,直接把话音开头当静音丢了。修复思路是"延迟丢弃"——数据永远进识别缓冲,静音只决定跑不跑推理,连续静音 2 秒才清积压。

**2 分钟版**:

1. **现象**:用户测试语音识别"断断续续"——每次只说一两个词(2 秒内说完)几乎全丢,连续说长句才正常。日志时间戳显示每次开口只蹦出零星字
2. **排查路径**:
   - 先从数据找规律:短句丢、长句只丢开头 → 指向"入口处丢数据"
   - 审查静音门控:静音时直接丢弃 PCM 不喂识别器。而静音标志**每秒更新一次**——用户开口的瞬间它大概率还是"静音",开头 0~2 秒被丢
   - 短句总共 2 秒 → 全灭;长句 → 只丢开头。现象完全吻合
3. **根因**:控制信号(静音标志)的更新频率(1s)远慢于被控事件(说话开始,毫秒级)——**这是"滞后"问题,不是"逻辑错"问题**,所以代码读起来"完全正确"
4. **修复**:改成"延迟丢弃":静音时数据**照常喂入**(语音开头完整保留),只是不跑推理(省 NPU 的目标不变);连续静音 2 秒才重建状态清积压,且距上次识别出词 2 秒内绝不清理
5. **沉淀**:任何"门控/丢弃"逻辑,先问"控制信号的滞后是多少、被滞后吃掉的部分能不能承受"。不能 → 延迟丢弃,别即时丢弃

**可能被追问**:
- Q:"静音怎么判定?" A:每秒统计 PCM 标准差,<100(约 -50dBFS)判静音
- Q:"不推理但喂数据,内存不涨吗?" A:连续静音 2 秒重建特征缓冲丢弃积压,内存有界

## 故事 5(备用):退出时崩溃——多线程的生命周期账本

**30 秒版**:程序 Ctrl+C 退出时随机段错误。审查发现清理顺序颠倒:RTSP 调度器先销毁,而音频采集线程的 lambda 里还捕获着它的指针,退出瞬间新音频到达触发回调 → 访问已释放内存。修复是把清理顺序改成"谁在用谁,谁先停"——先停全部音频生产者,再关 RTSP。

**沉淀**:退出路径要画"谁依赖谁"图。这个 bug 的教训后来被写进项目规范:凡是"线程 A 持有线程 B 的对象指针",B 的销毁必须在 A 停止之后。
