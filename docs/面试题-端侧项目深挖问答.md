# 一、编译与构建工具链

## 1. 你的交叉编译环境是怎么搭的?什么是交叉编译,工具链是什么?

**结论**:PC(x86)上装 RK3588 的 aarch64 交叉工具链,一键脚本 `build-linux.sh` 编译,产物经 adb 推板部署。

**细节**:
- 交叉编译 = 在 host 架构(x86)上生成 target 架构(aarch64)可执行文件的过程,前提是工具链三件套:**交叉编译器**(gcc/g++ 前缀 aarch64-xxx-linux-gnu)+ **sysroot**(目标平台的头文件与库)+ **链接脚本/ABI 约定**;
- 本项目用正点原子提供的 buildroot 工具链,`export CC/CXX` 后走原生 CMake 流程,没有用独立的 toolchain.cmake 文件——小项目够用,大项目建议 toolchain.cmake 规范化;
- **sysroot 的重要性**:交叉编译时默认 include/lib 搜索路径指向 host 的 /usr,必须显式指到 sysroot,否则链接到的库 ABI 不匹配(本项目 CMakeLists 里 `include_directories(${SYSROOT})` 就是这个作用);
- 部署验证:每次推板后本地 md5 与板端 md5 比对,防止传了一半的二进制上板运行(交接说明书里固化了这条协作约定)。

**加分句**:交叉编译只是工具,真正的坑在"目标平台运行时环境"(库版本、驱动版本)和宿主不一致,所以我养成了"每次构建都带版本信息、推板必验 md5"的习惯。

## 2. CMake 在你的工程里做了什么?第三方库怎么组织?

**结论**:一个 CMakeLists 管两个目标(SOC 主程序 + 可选 Piper TTS 开关),第三方库分三类管理。

**细节**:
- **SOURCES 显式清单**:所有 .cpp 显式列出(不 glob)——加新文件必须改 CMakeLists,换来的好处是增量编译正确、依赖关系可审计。本项目加 FrameProvider 时就靠显式清单避免漏编;
- **第三方库三分类**:
  1. 源码直接编入(cJSON、minimp4 等小库)——无版本管理成本,改起来快;
  2. 预编译 + 静态链接(live555、rga、mpp、rknpu2)——板端依赖最小,部署只需推一个二进制 + 动态 so 目录;
  3. 运行时动态库放 install 目录(rkllmrt/rknnrt)——与模型文件一起推板,`LD_LIBRARY_PATH=./lib` 运行;
- **开关式可选依赖**:Piper TTS 用 `-p` 命令行参数开 CMake 选项——板端没装 piper 依赖时也能编译出完整功能以外的可运行版本(能力降级,不阻塞主线);
- install 目录按 `install/rk3588_linux_aarch64/atk_rtsp_ai_server/` 组织(binary + lib + model),推板即"整个目录内容推到 /AI/"。

**加分句**:依赖管理的原则是"板端目标环境最小化"——能静态的静态,必须动态的集中放一个 lib 目录。

## 3. 编译优化级别怎么取舍?为什么 Release 版还保留那么多日志?

**结论**:`-O2`(Release),不追求 -O3/-Ofast——嵌入式上稳定性优先,而且热点根本不在 CPU 代码里。

**细节**:
- 性能热点分析:视频编码在 MPP 硬件、AI 在 NPU、缩放旋转在 RGA——C++ 侧只剩调度和轻量后处理,优化 CPU 代码的收益天花板很低,`-O2` 足够;
- -O3/-Ofast 的风险:浮点重排可能改变数值行为(后处理置信度计算不允许)、代码体积膨胀(板端 flash 有限)、偶发 miscompile;
- **日志与优化不冲突**:Release 版保留分层日志是因为嵌入式场景"现场不可复现"——出了问题只有日志能回溯。成本可控:统计类日志节流打印(每秒一行),高频路径不打印;
- 调试用 Debug 版的场景:core dump 分析、gdb 远程调试(板端 gdbserver),平时不用。

## 4. 链接错误 undefined reference 怎么排查?你遇到过哪些编译链接问题?

**排查顺序**:符号属于哪个库 → 该库是否在链接顺序里(静态库**顺序敏感**:被依赖的放后面)→ 符号是否被 C/C++ 名字修饰破坏(缺 `extern "C"`)→ 版本不匹配(头文件与 .so 版本不一致)。

**项目真实案例**:
1. **C++ 库被 C 代码引用**:paho-mqtt 是 C 库,头文件自带 extern "C" 保护,但自己封装的 C 接口给 C 文件用时必须手动包一层——第一次写封装就漏了,链接期报一堆 mangled 名字找不到;
2. **静态链接顺序**:live555 的库文件之间有依赖(groupsock → BasicUsageEnvironment → UsageEnvironment),链接顺序反了就 undefined reference,把被依赖的库放后面解决;
3. **符号版本**:板端 libpaho 版本与 PC 交叉环境版本不一致,运行时找不到符号——教训是交叉编译环境的库必须和板端逐版本核对(交接说明书里有记录)。

## 5. 头文件组织有什么讲究?config.h 全局配置你是怎么设计的?

**结论**:按层划分头文件(cpp/ 通用引擎层、TLServer/ 板端主程序层、rknpu2/ 第三方),全局配置收敛到 config.h + 唯一 config.cpp 解析。

**细节**:
- 头文件守卫 + 最小依赖:头文件只 include 自己声明所需的(前向声明 struct cJSON 而不是拉整个头);
- **config.ini 的设计**:全部可调参数(码率/分辨率/阈值/提示词/开关)放 ini,启动时解析进结构体,运行时零改代码;`saveDefault()` 自动生成带注释的默认配置文件——接手的人看文件就能懂所有参数;
- 关键点:老配置文件缺少新键时**走结构体默认值**——这就是每次加配置不用改板端老文件的原因(幂等升级);
- 头文件分层的好处:cpp/ 目录的引擎类(chat_engine/vlm_engine/tracker)与板端采集编码解耦,理论上可以单独编译成单元测试目标。

# 二、C++ 语言与内存

## 6. 你的项目用了哪些智能指针?分别在什么场景?

**结论**:`unique_ptr` 管独占资源(TTS 后端实例),`shared_ptr` 管跨线程共享的 promise(复核结果传递),其余用 RAII 对象管硬件资源。

**细节**:
- `std::unique_ptr<TtsBackend> tts_`:后端可插拔(piper/cloud),所有权唯一、换后端即 reset,出作用域自动析构;
- `std::shared_ptr<std::promise<...>> prom`:复核任务入队后,promise 同时被队列和等待方持有——请求方拿 future 等结果,执行方 set_value,谁先销毁都不会悬空;
- 硬件资源用 RAII 而非智能指针:Mppclass 析构里 mpp_destroy + 关闭所有 fd;ALSA 播放会话 session 对象内 open/finish 成对——资源生命周期与对象绑定,退出路径(信号中断)自动清理;
- 为什么不用裸指针跨线程传对象:ASR→chat 的回调只传 std::string 拷贝,chat→事件线程只传值——**跨线程不传指针**是降低并发 bug 面的第一原则。

## 7. std::future/promise 在跌倒复核里怎么实现"跨线程等一个结果"?

**流程**(这是本项目跨线程通信的核心模式):
1. 事件线程(发现跌倒候选)调 `requestFallConfirm(image)` → 创建 promise → 拿到 future → **任务入 urgent 队列**(锁保护的 deque + 计数) → 返回 future;
2. chat 线程(唯一能碰 VLM 的线程)在 loop 顶部优先消费 urgent 队列 → 执行复核 → `prom->set_value({verdict, reply})`;
3. 事件线程 `future.wait_for(12s)` 拿结果 → 超时按"无法确认"兜底直报(宁报勿漏)。

**为什么这样设计**:
- **线程归属红线**:VLM 引擎所有调用只允许在 chat 线程发生(同步阻塞 API,无内部锁)——future/promise 让"请求方任意线程、执行方单线程"解耦;
- **超时兜底**:`wait_for` 而不是 `wait`——复核链最坏情况(巡检占用中)实测 ~10.6s,12s 预算保证报警链路绝不因 VLM 卡住而哑火;
- 引擎未运行时立即返回就绪 future(verdict=2)——调用方零感知降级。

## 8. 右值引用和 move 语义用在哪?为什么句队列要 move?

**结论**:句队列/波形队列的 `std::deque<std::string>` 和 `std::deque<SynthItem>{pcm向量}` 全程 move 传递,消灭大对象拷贝。

**细节**:
- 一段 TTS 音频(PCM 16bit 采样)一句话就是几万~几十万样本(实测一句 3.4 万~7.5 万样本),拷贝一次就是几百 KB 内存搬运;`sent_q_.push_back(std::move(s))` 只转移指针,零深拷贝;
- 双队列流水线(句队列→合成→波形队列→播放)里每件数据只被一个消费者消费一次——**move 语义的前提就是"独占所有权"**,这里天然满足;
- 返回值优化之外,`std::move` 还有一个陷阱讲过:move 之后的对象处于"有效但未定义"状态,代码里 move 完立即清空/不再读——项目里 move 后从不复用原对象。

## 9. RAII 怎么体现在资源管理上?

**结论**:硬件上下文(MPP/RKNN/ALSA/fd)全部"构造获取、析构释放",信号中断的退出路径零泄漏(日志可证:退出时 MPP 资源释放、VIDIOC_STREAMOFF、所有线程 join)。

**具体清单**:
- Mppclass:InitMpp 分配 ctx/缓冲池/头信息,析构 Close() 依次 mpp_buffer_put → cfg deinit → mpp_destroy;
- VLM 引擎:init 建 rkllm/vision 上下文,destroy 只允许在 chat 线程退出后调用(无并发 run);
- PlaybackSession:open/finish 成对,句间 gap 写静音,退出时保证 finish(历史上 ALSA 尾静音写入曾是卡死点,专门修过);
- 线程也纳入 RAII 思维:ChatEngine::stop() 顺序 = 置 running 标志 → 唤醒所有条件变量 → join 三个线程 → 释放 VLM——顺序本身有讲究(先打断 run 再 join,否则退出慢 8 秒+,实测过)。

**加分句**:RAII 的极致是"异常路径也安全"——C++ 析构保证即使信号中断,清理代码也会执行;项目退出日志里每一行"资源释放完成"都是 RAII 的证明。

## 10. 多态怎么用的?为什么 TTS 后端要设计成可插拔?

**结论**:`TtsBackend` 抽象基类(synth 接口)+ 两个实现(云端火山 TTS、本地 Piper),工厂函数按配置实例化——同一个语音链路换后端零改动。

**动机**(真实演进):项目最初 TTS 走云端(火山,端到端 4.5s),后来为了**全离线**加入本地 Piper(首句延迟 14s→3s 的流式流水线也基于它)。后端差异只在"文本→PCM"这一步,播放/队列/回声门控全部复用;
**多态的代价思考**:虚函数调用开销在音频路径可忽略(毫秒级 vs 秒级音频);真正要避免的是"用多态装所有东西"——本项目的 VLM/ASR 没有抽象层,因为它们只有一个实现,抽象是多余的(面试官喜欢听"我拒绝过度设计")。

## 11. 项目里野指针/越界/内存泄漏的真实案例怎么排查的?

**三件真实案例**(每个都有一套定位流程):
1. **流式 ASR fbank 特征缓存泄漏**:每帧特征累积不清,内存缓慢上涨。定位:板端 RSS 曲线 + 代码审计 fbank 对象生命周期 → 修复:状态清理函数里重建 fbank 并归零计数。教训:泄漏不一定崩,先看"涨不涨";
2. **UTF-8 截断越界类 bug**:按字节截断长文本,截断点落在多字节字符中间 → 输出末尾孤立引导字节 → 乱码(�)。定位:巡检摘要偶发乱码 → 最小复现(特定长度中文) → 修复:截断点向前回退到字符边界(0b10xxxxxx 续字节不能作开头);
3. **悬空回调**:VLM 流式回调指针(on_delta_)是跨轮复用的成员,run 返回后必须立刻置空——防上一轮的增量转发到下一轮对象。原则:**回调的生命周期显式管理,用完即清**。

**方法论总结**:板端不一定能跑 ASAN,所以顺序是"现象定位(日志二分)→ 最小复现 → 代码审计 → 修复 + 回归"。

# 三、Linux 系统与驱动接口

## 12. 为什么多线程而不是多进程?线程怎么命名、怎么设优先级?

**结论**:单进程 10+ 线程——数据共享频繁(队列/缓冲),线程共享地址空间天然适合;进程隔离的成本(IPC、内存复制)在嵌入式上不划算。

**线程治理细节**:
- **pthread_setname_np 命名**:chat_llm/tts_synth/tts_play/采集/AI/编码×2……命名之后 top/日志一眼分清是谁在吃 CPU——排障效率的前提;
- **优先级分档**:chat_llm nice 10、synth/play nice 15(低优先级,不抢视频/AI);ASR 推理线程绑大核 + NPU 中断绑核(RTF 0.47→0.087 的优化手段之一)——实时性线程给调度器让路的优先级设计;
- **线程职责单一**:每个线程只做一件事(采集只采集、AI 只推理、chat 只调度 VLM)——这比"几线程"更重要,是架构可解释性的基础。

## 13. 信号处理:优雅退出是怎么做的?

**结论**:注册 SIGINT/SIGTERM handler → 置退出标志 → 各线程在自己的循环检查点退出 → 主线程 join 所有线程 → 发布 MQTT offline 状态 → 释放资源。

**细节**(日志可证):"收到退出信号,开始清理资源..." → 主/子码流线程退出(VIDIOC_STREAMOFF)→ ASR flush 尾段 → 发布 `{"state":"offline"}`(retained,监护人侧立刻知道设备离线)→ 所有线程 join → 退出;
**要点**:
1. handler 里只置 flag(信号上下文里做重活是危险写法);
2. 阻塞中的线程靠"标志 + 条件变量 notify_all"双保险唤醒(退出时 stop() 把所有 cv 全唤醒——这就是之前长对话死锁时按 Ctrl+C 能退出的原因);
3. 退出顺序有讲究:先打断 rkllm_run(abort),否则 join 要等完整生成(实测多等 8s+)。

## 14. V4L2 采集链路:MPLANE/DMABUF/QBUF 流程,为什么要 DMABUF?

**流程**:open(/dev/videoX) → QUERYCAP → S_FMT(NV12,MPLANE)→ REQBUFS(V4L2_MEMORY_DMABUF)→ 循环 QBUF/DQBUF → STREAMON。

**为什么 DMABUF**(三层递进):
1. 传统 mmap 方式:驱动内存映射到用户态,用户 memcpy 到编码器缓冲——每帧一次全帧拷贝;
2. DMABUF 方式:**编码器(MPP)先分配输入缓冲并导出 fd**,V4L2 把 fd 导入(QBUF),ISP 通过 DMA 直接写进编码器的缓冲——数据只在 DMA 总线上流动,CPU 零介入;
3. 定量收益(双重验证):①membench 带宽基准——4K NV12 单次拷贝 1.34ms(DDR 冷拷贝 9.5GB/s);②**A/B 对照实测**(config extra_copies 开关模拟插入全帧拷贝)——主码流 LatAvg 10.8→17.9ms(+66%,稳态单拷贝 1.85ms,两者互相印证),即零拷贝每帧省 ~7ms + ~1.1GB/s DDR 带宽 + 单核 ~12% CPU;子码流(460KB)收益 <0.2ms——零拷贝大头在 4K 主码流。A/B 实验还暴露了单 RGA 引擎的排队相位现象(带拷贝轮 DetectLag 锁死 48ms、基线轮漂移),是"对照实验发现隐藏问题"的好例子。

**MPLANE 是什么**:NV12 的 Y 平面和 UV 平面物理分离存储(两个内存地址)。硬件编解码器要求平面分离,MPLANE 格式免去"拼平面"这一次拷贝。

## 15. mmap 底层原理?和 DMA 打交道的缓存一致性怎么解决?

**mmap 原理**:建立虚拟地址→物理页的页表映射。首次访问触发缺页,内核把目标页填进进程页表;之后访问是纯硬件地址翻译,零拷贝零系统调用。

**本项目 mmap 的用途**:CPU 必须碰数据的环节(AI 画框)把 CMA 分配的 dma-buf mmap 进来直接写像素。

**缓存一致性(项目真踩过坑)**:带缓存的 mmap 映射,CPU 写框进的是 cache 行,DMA(RGA/编码器)读的是内存——两边不一致 → 实测现象:AI 框拖影、闪烁。标准解法是 **dma-buf 生态的 `DMA_BUF_IOCTL_SYNC`**:
- CPU 读前:`SYNC_START | READ`(失效缓存,强制从内存取);
- CPU 写后:`SYNC_END | WRITE`(刷出缓存,让 DMA 看到);
- 括号必须**完整成对且无条件每帧执行**——项目历史 bug:只在"干净帧快照"路径做了 START,画框路径没做 → 拖影复发。教训:**零拷贝不等于零问题**,CPU/DMA 共享内存的同步是必修课。

## 16. ALSA 播放与采集:回声怎么处理?播放与采集并发会怎样?

**结论**:单声卡播放+采集并发会 xrun 损坏采集流,项目用"播放期间暂停采集 + ASR 侧回声门控"双保险。

**细节**:
- **现象级知识**:喇叭出声会被麦克风收回去,ASR 会把 TTS 播报词识别成用户说话(误触发对话/求救词);
- 解法一(硬件调度):play_state 回调 → 播放开始 `pauseCapture()`、结束 `resumeCapture()`——规避并发 xrun;
- 解法二(软件门控):`suppress_input_` 原子标志,播放期间 ASR 解码出的 token 全部丢弃(连同已在管道里的文字一起清);
- **踩过的坑**(本周真实 bug):"本轮播报完成"的标志位漏置 → 门控永不解除 → 采集永久暂停 → 第一次对话后 ASR 彻底失活。修复后 play 结束时严格成对回调 false;
- 采集侧还有静音自检:启动时检查信号标准差(≈0 提示麦克风未接/增益为 0)。

## 17. /sys 节点调试:thermal/devfreq/cpufreq,你的 watchload 工具怎么实现的?

**结论**:板端性能工具 watchload(V1.4 自研)读 /sys + /proc + psutil,终端实时显示 NPU/CPU 负载、内存、温度、频率。

**实现细节**:
- NPU 负载:`/sys/kernel/debug/rknpu/load` 正则解析三核百分比;
- 温度:遍历 `/sys/class/thermal/thermal_zone*/temp` 取最大值(温升降频会拖慢推理);
- 频率:`/sys/class/devfreq/*npu*/cur_freq`(**单位 Hz**,除 1e9)与 cpufreq policy(**单位 kHz**,除 1e6)——两个接口单位不同,工具 V1.4 踩过 1000GHz 的显示 bug;
- 内存:psutil + /proc/meminfo 的 CmaTotal/CmaFree(多媒体连续内存,本项目 dma-heap 分配来源);
- Top3 进程 RSS 用于长稳测试盯泄漏;
- 设计取舍:终端模式用 curses 画条(串口非 UTF-8,色块字符会乱码所以用 '#')。

## 18. Linux 内存语义:used/cache/available 有什么区别?为什么模型权重不计入 used?

**结论**:used 是匿名内存,buffer/cache 是文件页缓存,available 是"现在可用的内存"(含可回收 cache)。模型权重是文件映射页,计入 cache 不计入 used。

**项目实测数据**:TLServer RSS 3.3G,但系统 used 只有 1.25G——差的 ~2G 就是 Qwen3-VL-2B 权重文件页躺在 page cache 里。空闲时内核回收部分文件页,RSS 降到 2.5G(不是泄漏——泄漏只涨不降)。

**面试意义**:这个数据证明我理解"程序 RSS"和"系统 used"的口径差异,以及**文件映射模型加载的真实内存成本**(首次推理 page fault 重新读页)。顺带:MEM% 的定义是 (total−available)/total,包含可回收缓存——这就是为什么板端 16G 内存平时 26% 是个稳定值。

## 19. swiotlb/CMA/dma-heap 是什么?你踩的坑和解决方案?

**背景知识**:
- **CMA**:内核启动时保留的连续物理内存区,给需要大块连续内存的 DMA 设备用(摄像头/编解码器/RGA);
- **dma-heap**:用户态申请 dma-buf 的标准接口(`/dev/dma_heap/cma`),本项目 MPP 编码缓冲全从这里分配;
- **swiotlb**:IOMMU 缺失时,DMA 设备访问不连续内存的"软件弹跳缓冲"——设备 DMA 写进池子,CPU 再拷贝出来。

**事故链(项目最大坑)**:主码流升级 4K 后,4K 缓冲 12.4MB,RGA 对 rknn 导出的不连续 dmabuf 走 swiotlb 弹跳 → 大块槽段把池子碎片化耗尽 → `swiotlb buffer is full` → **所有** RGA 任务挂掉(子码流一并遭殃)+ 周期性报错。

**解决**:全链路缓冲改 CMA 连续内存分配 + 完整 dma_buf_sync 括号。**三次对照实验**闭环结论(4K 条件下 rknn dmabuf 进 RGA 必失败,CMA 不失败),代码注释写明实验证据防后人回退。

# 四、项目业务逻辑与架构

## 20. 为什么双码流?主码流和子码流各干什么?

**结论**:主码流高清给人看/录像,子码流低清给 AI 推理——由摄像头 ISP 硬件同时输出两条流,互不干扰。

**细节**:
- AI 不需要高清:yolov8n-pose 输入 640x480,分辨率越高 NPU 越慢、收益为零;
- 主码流需求演变:最初 1080p → 用户要"大视野+高清" → **4K 采集 + RGA 硬件缩放 + 1080p 编码**(正点 BSP 的 rkisp 只有 1080p/4K 两种尺寸可用,1920x1440 等中间尺寸有双画面 bug——实测试出来的);
- 两条流的硬件路径完全独立(各自 V4L2 设备 + 各自 MPP 实例),AI 框只画在子码流;
- 帧率:双路恒 30fps,编码延迟 10ms 级,常驻 CPU ~2%(全硬件化)。

## 21. 为什么两级检测,而不是 YOLO 直报?

**结论**:YOLO 高召回但误报多(挂画、蹲下捡物、照片都像跌倒),VLM 看图语义理解可以排除——感知级求"不漏",语义级求"不误",两级各司其职。

**实测证据**:照片场景(合影挂画)被 YOLO 恒定检出为"人"(Persons=1 持续),跌倒候选反复触发,但 VLM 复核判定"这是照片"→ cleared 分级,零误报警。单级方案要么漏报要么被误报淹没。

**成本核算**:复核只在候选触发时调用(事件驱动,不是每帧),每次 3.5~7s、12s 超时兜底"宁报勿漏"——用延迟换准确率,换来的是报警可信度(监护人收到 urgent 是真该行动的)。

## 22. 追踪器为什么自研 IoU 匹配,不上 DeepSORT/卡尔曼滤波?

**工程判断**(面试官想听"为什么不上"):
1. 场景约束:家里 1~3 人,AI 帧率 15fps,帧间位移小——IoU 贪心匹配(全矩阵取最大对)在低速多目标下已经够用;
2. DeepSORT 的核心增量是 ReID 特征网络(外观特征辅助匹配)+ 卡尔曼运动预测:ReID 网络要额外 NPU 算力,卡尔曼对"站着不动/躺倒"这类低速目标收益极小;
3. 复杂度换来的 ID 稳定性,我用更便宜的方案拿到了:**漏检宽限 60 帧**(≈4s,目标短暂消失不删 ID)+ 子框抑制(脸部误检不当新人)+ 恢复迟滞——实测 ID 从"涨到 236"变成稳定 1~5。

**加分句**:算法选型的第一问是"我的数据分布和资源预算",而不是"最新的是什么"。如果哪天要室外多行人密集场景,再上 DeepSORT 不迟。

## 23. 跌倒报警为什么设计三道闸门?分别解决什么问题?

**结论**(照片场景实测逼出来的设计):①单人武装位(armed)防同一次跌倒无限重报;②场景挂起(scene pending)防"换 ID/换人"绕过单人状态;③冷却(15s)防瞬时抖动重复。

**三个真实翻车史**:
1. 照片放摄像头前 → 每 15s 报一次警(冷却一到又报)→ 引入 armed:报警后必须连续 15 帧(≈1s)非跌倒才重新武装;
2. 旋转照片测试:正常姿态后转回跌倒不报警 → 场景挂起没有解除条件 → 三解除条件:有人恢复且无人跌倒 / 30s 无跌倒检测 / 5 分钟硬超时(持续倒地每 5 分钟重提醒一次);
3. ID 抖动绕过一切:同一次跌倒 ID 6→9→15 重建 → 场景级挂起挡住。

**设计思想**:单人状态机防"重复",场景级保险丝防"绕过",冷却防"抖动"——三层各管一种失败模式,面试时能画状态图。

## 24. 漏检宽限为什么是 60 帧?绘图层为什么只画 30 帧内的?

**结论**:追踪层宽限 60 个 AI 帧(≈4s)保 ID 稳定,绘图层只画最近 30 帧(≈2s)内的目标——"内部保留"和"视觉呈现"分离。

**为什么 60**:实测 YOLO 对静态照片的检测间歇"出现 1-2s 又消失 1-2s"(15~30 帧),宽限必须显著大于间歇才防得住 ID 重建;60 帧是 4s,留了裕量。

**为什么绘图只 30**:人走出画面后,追踪层还要留 4s 防抖动,但框还画在空地上就变成"没人的地方检测出框"(用户实测反馈)——绘图层限 2s,鬼影框最多停留 2s,而报警投票逻辑仍在追踪层完整保留。

**设计思想**:一个数据结构,两个消费方(报警逻辑要稳,视觉呈现要跟手)——通过"绘制滞后期"分开,而不是让报警逻辑迁就观感。

## 25. 优先级仲裁四层怎么协同?rkllm_abort 的安全性怎么验证?

**四层调度**(复核 1 > 语音 2 > 远程 3 > 巡检 4):
1. **优先级队列**:复核走独立 urgent 通道(与主事件队列分离,任何状态先消费);
2. **rkllm_abort 抢占**:复核到达时若语音轮在生成,跨线程 abort 打断(rkllm_abort 官方支持外部打断,且只在 `rkllm_is_running` 为真时调用);
3. **句级丢句**:播放线程句间检查抢占位,丢弃未开播句(当前句自然播完 ≤3s)——复核优先于播报;
4. **超时降级**:复核 12s 超时按"无法确认"直报 attention(宁报勿漏)。

**实测效果**:巡检期间 YOLO 帧率 15→3fps 但 2s 恢复、主码流 30fps 零影响;长对话中途跌倒 → abort 打断成功(用户实测确认)。**abort 的边界**:vision 编码阶段 rknn 无 abort API,让路点设在"编码完成→生成开始前"检查 abort 标记——抢不动 prefill,就抢在 decode 之前。

## 26. 巡检的执行条件为什么那么多约束?TTS 播放撞上巡检怎么办?

**巡检条件**:enable && interval>0 && 状态 IDLE && 有人 && 距上次对话 ≥10s && urgent 队列空。

**每条约束的理由**:IDLE(对话中不打断)、有人(无人帧零 VLM 调用,省 NPU)、min_idle 10s(刚聊完天不抢 NPU)、urgent 空(给复核让位)。

**与 TTS 播放的冲突**:不存在——巡检检查和语音对话都在 chat 线程,**同一线程天然串行**,播放时线程阻塞在等待上根本不会去巡检;播放结束后还有 min_idle 10s 顺延。代价是巡检会"晚点跑"(频繁对话场景实际间隔拉长),这是有意的取舍:对话体验优先于巡检时效。

**连轴转防护**(实测过"复核刚结束→巡检立刻开跑")、远程问答、跌倒复核、语音问答三条路径结束时都顺延巡检一个完整周期。

## 27. FrameProvider 按需快照:为什么不做 30fps 全量转换?

**结论**:抓帧给 VLM(复核/巡检/远程问答/视觉轮)是**低频事件**,而 30fps 全量 RGB 转换的 CPU 成本是持续的——用"请求时才转换"的门控把平时开销压到零。

**实现**:
- 采集线程每帧检查 `want_` 原子标志:平时零开销(一次原子读);被请求时转换+clone 换槽 + 序号自增;
- 请求方 `request(timeout)` 置 want_ → 等序号变化 → 拷贝返回,延迟 ≤1 帧(33ms);
- 线程安全分析:槽位 clone 在采集线程完成才落槽,请求方读的是完整快照,无跨线程访问采集缓冲。

**量化**:30fps 全量 cvtColor 约 60-90ms/s CPU——对一个常驻 CPU ~2% 的系统,这是不可接受的持续开销;按需方案只在巡检(30s 一次)、复核(事件触发)时付账。

## 28. MQTT 协议设计:topic 分层/req_id/retained/token,断线重连怎么处理?

**Topic 设计**:上行 home/fall(报警,retained)+ home/{device_id}/timeline(时间线)+ resp(命令应答)+ state(在线状态,retained);下行唯一入口 home/{device_id}/cmd。**多设备隔离**靠 device_id 占位符,加载时替换。

**协议要点**:
- **req_id 关联**:命令与应答配对,客户端能关联"哪个请求的结果";
- **retained**:报警/状态消息 broker 保留最后一条——监护人 App 后上线也能拿到最近一次状态(为什么报警要 retained:断线期间的事故不丢);
- **token 认证**:不等长比较(逐字节 XOR 累积,常数时间)防时序侧信道攻击,失败仅回 401;
- **断线重连**:paho 同步客户端 + keepalive 15s 心跳,连接断开重建后**必须重新 setCallbacks + 重新 subscribe**(历史上踩过"订阅失效收不到命令"的坑);
- **回调线程红线**:MQTT 回调只入队不执行(解析/执行在 chat 线程),避免回调线程直触 VLM/DB 的并发问题;
- 收到下行命令实测问题:paho 的 msgArrived 回调在同步 receive 模式下不可靠 → 改为 poll 时直接处理。

## 29. 录像:预录 5s 怎么实现?fMP4 为什么断电安全?切片为什么 IDR 对齐?

**预录 5s**:循环缓冲(环形队列存最近 5s 的编码帧),事件触发时把缓冲内容 + 后续 5s 写入事件文件——事故前 5 秒的画面不靠"先知"。

**fMP4 断电安全**:传统 MP4 的 moov 元数据在文件尾,断电即损坏;fMP4(fragmented)把 moof/mdat 分片交错写入,**每个分片独立可播**,断电只丢最后一个分片。事件录像这种"写一半断电也要能放"的场景必须 fMP4。

**切片 IDR 对齐**:P 帧依赖前面的帧,切片必须从 IDR 帧开始写文件,否则切片前几帧花屏——项目里从 MPP 包标志位判断 IDR,GOP 主码流 1s/子码流 0.5s,切片起点对齐误差受控。参数集(VPS/SPS/PPS)每个切片文件头都要注入,否则独立文件无法播放。

## 30. 产品决策三连:为什么跌倒静默报警?为什么确认后要慰问?为什么关键词触发视觉轮?

**静默报警**(最初设计):报警接收方是监护人,跌倒者可能昏迷——现场语音无救助价值且干扰;复核后不追加生成+播放,报警更早发出;语音通道语义上只服务老人**主动发起**的交互。

**确认后慰问**(后来加):静默的是"确认过程",确认真跌倒后 VLM 在同一次调用里产出慰问语("保持不动,等待救援")现场播报——报警(给监护人 MQTT)和慰问(给现场语音)两路各司其职,不矛盾。这也修正了"静默=冷血"的观感。

**关键词触发视觉轮**(而不是每轮带图):语音对话默认纯文本(响应快),问句命中"看到/画面/谁在/好痛"等词才抓帧带图(vision 编码 3s 的代价只在需要时付);求救词链路无条件带图(救命时 VLM 必须看见现场)。**权衡**:换说法没命中关键词时模型看不到画面——用代价可控的漏网换大多数轮次的低延迟,可接受。

# 五、AI 推理与部署优化

## 31. RKNN 模型部署流程?版本三层关系是什么?

**流程**:PyTorch 模型 → 导出 ONNX → RKNN-Toolkit 转换 + 量化 → .rknn 文件 → 板端 librknnrt.so 加载推理。

**版本三层关系**(升级时逐层核对,踩过坑):
```
模型格式版本(rknn-toolkit2 转换时决定)
   │ 只能被 ≥ 自己版本的 runtime 加载
   ▼
librknnrt.so runtime(板端推理库)
   │ 运行需要内核驱动支持
   ▼
内核 NPU 驱动(本项目 v0.9.8)
```
排查"模型加载失败"的顺序永远是:驱动版本 → runtime 版本 → 模型格式版本。本项目升级 2.0.0→2.2.0 实测 AI 推理 47.5ms→45.3ms,升级收益要量化了再升。

## 32. INT8 量化基本原理?精度损失来自哪里?hybrid 量化是怎么回事?

**原理**:`q = round(x/scale) + zp`,推理用 int8 MAC 替代浮点;权重体积与带宽需求降 4 倍,NPU int8 算力数倍于浮点。

**精度损失来源**:①离群值(个别通道范围极大,一个 scale 兜不住);②逐层误差累积;③粒度太粗(per-tensor vs per-channel)。

**hybrid 量化案例(本项目)**:全 INT8 量化后 mAP 没崩,但**关键点置信度分数全部失效**——置信度被压缩到失效区间,下游阈值判定全乱,跌倒分类报废。解法:置信度相关层保留 FP16、其余 INT8。教训:**量化验收要看下游任务指标,不能只看 mAP**;部署工程师的价值就是在这种"工具链缺陷"面前给出可落地的绕行方案。

## 33. RKLLM 部署 2B VLM 的内存布局?KV Cache 是什么、为什么必须用?

**内存布局实测**:TLServer RSS 3.3G ≈ 2G 模型权重(文件映射页,计 page cache)+ ~1G 匿名内存(缓冲/堆)。16G 板子完全放得下,还有 11G+ 可用。

**KV Cache 原理**:自回归生成时,历史 token 的 K/V 每步都会重算——缓存起来,新 token 只算自己的 K/V 再拼接,总计算量 O(n²)→O(n),生成速度差一个数量级,现在大模型推理几乎必用。

**内存开销**:`2 × 层数 × KV头数 × 头维度 × 序列长度 × dtype`。端侧场景序列短、单用户,开销可控,但服务场景并发一多就是显存大头(PagedAttention 的由来)。

**本项目落地点**:RKLLM `keep_history=1` 保留多轮 KV(每轮只喂新增 user 输入);复核/巡检/远程/视觉轮调用前 `clearHistory(true)` 隔离(保留系统人设段);踩过的坑——同会话历史已有图像时再跑多模态,输出 `<|image_pad|>` token 洪泛([PAD151935] 连发整轮),根因是 KV 里旧图像嵌入错位,修复为图像调用前清 KV + 输出端剥离 pad token 双保险。

## 34. prefill 和 decode 两个阶段有什么不同?和你的抢占设计什么关系?

**prefill**:全部输入 token 并行过模型填 KV,**计算密集**,决定首 token 延迟(TTFT)。
**decode**:逐 token 自回归,**访存密集**(每步读整个 KV),决定每 token 延迟(TPOT)。

**项目映射**:
- vision 编码 + 提示词处理 ≈ prefill:实测 3.1~3.2s(与 YOLO 争抢时),NPU 三核 97/40/75% 全动员;
- 文本生成 ≈ decode:流式回调逐句进 TTS,实测 ~20 字/秒(争抢工况);
- **抢占让路点卡在两阶段之间**:rknn 的 vision 编码没有 abort API,所以复核到达时若恰在编码中,只能等编码完成后检查 abort 标记、跳过生成直接让位——抢不动 prefill,就抢在 decode 开始前,节省的生成段 3-4s 就是复核链 12s 预算的关键。

## 35. 评估推理性能看哪些指标?为什么你加了 AIwait/DetectLag 两个自研指标?

**标准指标**:TTFT、TPOT、吞吐、p50/p95 分布、RTF(语音实时率)、内存(RSS/KV)、温升。

**自研指标的故事**(面试亮点):巡检期间发现 YOLO 帧率 15→3fps,若只看"均值推理耗时"(23ms→383ms)会误判成"推理变慢"。我加了两个指标把原因拆开:
- **AIwait**:帧在队列里等 AI 线程的时间(实测 0→413ms)——反映"排队";
- **DetectLag**:追踪器最后更新时间距今(峰值 263ms)——反映"框旧了多久"。
拆开后真相:p50 全程 23ms 不变,**降帧是 NPU 被 VLM 抢走导致的排队,不是推理慢**。没有这两个指标,这个诊断就做不出来——"把慢和等分开"是性能分析的第一原则。

## 36. 推理延迟不达标,排查思路是什么?

**四步法(每步都有项目实证)**:
1. **分层打点**:链路拆段(采集/预处理/推理/后处理/编码),每段时间戳——瓶颈一目了然(vision 3.2s / 生成 3.7s / 编码 10ms);
2. **区分慢和等**:查排队指标(AIwait 0→413ms)——一半的"延迟问题"是调度问题不是性能问题;
3. **对照实验**:一次一个变量(swiotlb 问题三次对照实验闭环:rknn vs CMA × 4K 开/关);
4. **查资源边界**:同步看温度(是否降频)、内存、带宽——watchload 实测温升仅 4°C 排除降频因素,才能锁定调度方向。

**总结**:定位瓶颈 → 区分原因 → 对照验证,顺序不可颠倒;上来就调参是最低效的排查。

## 37. 换一个 NPU 平台/遇到不支持的算子,你会怎么处理?

**处理路径(成本从低到高)**:
1. **算子替换/拆解**:用等价算子组合实现;
2. **规避性改模型**:导出时绕开该算子(换实现/改结构)——本项目 hybrid 量化就是这个思路的实例(不换模型结构,换导出策略:敏感层走 FP16);
3. **自定义算子**:平台 SDK 支持时注册实现,或 CPU 兜底执行;
4. **图拆分**:整段子图在 CPU 执行,其余在 NPU——拆分点选数据量小的位置(搬移成本低)。

**换平台的整体方法**:模型重走"导出→转换→量化→验证"流水线,所以我把验收自动化(离线自检工具链:合成数据 5/5 通过率验证分类器),换平台时回归成本可控。**部署工程师的核心素养:快速判断问题在哪个层**(模型结构/导出工具/runtime/驱动),本项目 RKNN 版本三层关系的排查经验就是这套思维。

# 六、调试与工程方法论

## 38. 日志体系怎么设计?为什么 Release 版留这么多日志?

**设计**:分层 + 节流 + 诊断统计。
- **分层**:启动/配置日志、链路关键事件([Chat] 用户/[Confirm] 结论/[Patrol] 摘要)、统计行([SUB]/[MAIN] 每秒一行 fps/延迟分布)、诊断行([DRAW] 3s 带框比例、[POSE] 分类细节);
- **节流**:高频路径只打印聚合统计,不逐帧打;
- **诊断性统计的实战价值**:[DRAW] 带框=90/无框=0 一次锁定"框闪烁源头在检测侧还是编码侧";[SUB] 的 AIwait/DetectLag 拆开"慢 vs 等"。

**为什么留着**:嵌入式现场不可复现,日志是唯一的回溯手段;stdbuf 行缓冲 + tee 落盘,崩溃也不丢最后几行。代价(磁盘/性能)在统计节流下可忽略。

## 39. 偶发 bug 怎么复现和定位?对照实验怎么设计?

**方法论**(项目全部偶发 bug 的通用解):
1. **扩大采样**:偶发 ≠ 不能复现,把频率放大(更快的触发周期、更长运行时间);
2. **相关性分析**:观察现象与什么相关(时间?负载?另一个任务?)——框闪烁与"VLM 触发"相关,直接缩小到内存压力方向;
3. **对照实验三要素**:一次只变一个变量、对照组和实验组同环境、结论要能预测现象(swiotlb 案例:rknn vs CMA × 4K 开/关,四象限验证后结论唯一);
4. **记录证据**:每次实验的日志/截图归档,结论写进代码注释(防后人回退)。

## 40. 板端调试工具有哪些?你自己造了哪些工具?

**标准工具**:dmesg(内核报错)、gdbserver(远程调试)、perf/top/ps、watch -n1 cat /proc/xx。

**自研工具**(都是为项目痛点造的):
1. **watchload V1.4**:NPU/CPU 负载 + 内存(含 CMA)+ 温度 + 频率的终端仪表盘——巡检期 NPU 97% 的证据就来自它;
2. **membench**:DDR memcpy 带宽基准——零拷贝收益的对照实验工具(L3 逐出修正版,4K 单次拷贝 1.344ms 的数据来源);
3. **离线自检工具链**:合成数据验证姿态分类器(5/5 通过),板端不好跑的验证移到 PC 跑;
4. **watchload 的教训**:devfreq 单位 Hz vs cpufreq 单位 kHz——自研工具先踩单位坑,也是"读 sysfs 要查 ABI 文档"的实证。
