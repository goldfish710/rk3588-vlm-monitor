# 12. 踩坑实录:这个项目真实修过的八个 bug

> 每个 bug 都是真实发生、真实定位、真实修复的。学 bug 比学功能更值钱——
> 功能只会用一次,错误的思维模式会犯一百次。每个案例的结构:
> 现象 → 定位过程 → 根因 → 修复 → 思维教训。

---

## Bug 1:退出时 Segmentation fault(use-after-free)

**现象**:Ctrl+C 退出,日志打到"编码线程已退出"后直接崩溃。

**定位**:崩溃点在退出清理路径。审查清理顺序:

```cpp
Medium::close(server);
delete scheduler;              // ← scheduler 先死了
// ...
audio_cap.shutdown();          // ← 采集线程此时才停!
```

采集线程的 RTSP 音频 sink 是个 lambda,**捕获了 scheduler 指针**,每当有新音频就调 `scheduler->triggerEvent(...)`。scheduler 删除后,采集线程还在跑 → 一触发就是访问已释放内存。

**根因**:**对象生命周期与使用者的停止顺序颠倒**。谁在用谁,谁就得先停。

**修复**:清理顺序重排——先停音频生产者(采集线程退出,不再触发事件),再 close RTSP/scheduler。

**思维教训**:退出路径要画"谁依赖谁"图。凡是"线程 A 持有线程 B 的对象的指针",B 的销毁必须在 A 停止之后。这个 bug 在几乎所有多线程服务里都以各种面目出现。

## Bug 2:double free 崩溃

**现象**:TTS 播放完成后 `free(): double free detected` 直接 abort。

**定位**:播放函数重写时,新代码中途已经 `fclose(f)`,函数结尾的旧 `fclose(f)` 没删——同一个 FILE* 关两次。

**根因**:大段代码替换时,新旧代码的**资源所有权边界**没对齐。

**修复**:删除结尾的重复关闭,并留注释"f 已在前段关闭,此处不可再关"。

**思维教训**:修改有资源管理的函数时,先在纸上标出"谁在哪个位置释放",替换后逐条核对。RAII 的析构函数版本不会有这个 bug——又一次印证"资源自动管理"的价值。

---

## Bug 3:chunked 解析丢数据(语义错误)

**现象**:板端调 DeepSeek 流式接口,日志报"SSE 流未正常结束";PC 用 curl 完全正常。

**定位**:先 PC 复现——把我们的 HttpsClient 编译成 PC 测试程序连真实 API,打印响应体:`[DONE]` 缺失,且 body 大小恰好等于最大 chunk 的大小。锁定 chunked 读取函数:

```cpp
// 错误语义:把 n 当"目标大小"
bool readExact(..., size_t n, ...) {
    while (body.size() < n) { ... }   // body 已经 562 字节时,读 278 的调用直接跳过!
}
```

调用方传的是**增量**(本块 278 字节),实现按**总量**理解——前几个小块全部被跳。

**修复**:记录起始位置,按增量读:

```cpp
size_t start = body.size();
while (body.size() - start < n) { ... }
```

**思维教训**:函数语义(增量 vs 目标)要在命名/注释里写死;网络协议解析**必须在 PC 上写独立测试程序对比 curl 验证**,别直接上板——板端日志只能告诉你"错了",PC 测试能告诉你"错在哪"。

## Bug 4:唤醒词误触发 help_call 报警

**现象**:用户喊"你好"(唤醒词),MQTT 收到了 help_call 事件。

**定位**:唤醒词和呼救词共用 ASR 关键词表,而 MQTT 上报回调对**所有**命中词一视同仁。

**根因**:**一个机制被两个语义不同的消费者共用**,消费者没做过滤。

**修复**:MQTT 回调里过滤唤醒词(`if (kw == wake_word) return;`),唤醒词只走对话引擎。

**思维教训**:复用机制时,先问"这个机制对所有使用者语义一致吗"。不一致,就显式分流——用注释写清楚"谁不该走到这"。

## Bug 5:播放无声,退出时才出声(dmix 阻塞)

**现象**:TTS 播放日志正常但无声;Ctrl+C 退出瞬间声音突然出来。

**定位**:板端实验矩阵——aplay 播放 + 板载 mic 录音分析能量:
- TLServer 停止时:喇叭有声(峰值 4724)
- TLServer 采集运行时:`aplay -D default` **永久阻塞**(>5 分钟无返回)

**根因**:ALSA `default` 设备(dmix 软混合)与 `hw:0,0` 采集并发时 writei 阻塞;退出时采集停止、阻塞解除,积压音频才放出来。

**修复**:播放改 `hw:0,0` 直连硬件。紧接着发现新约束:采集 44.1kHz 时播放也被锁 44.1kHz("Rate doesn't match"),于是播放前把 16k TTS 音频上采样到 44.1k;又发现硬件最少 2 声道,mono 复制为双声道。

**思维教训**:
1. "正常但无声/阻塞"优先怀疑设备路由与并发冲突,而不是代码逻辑
2. 硬件问题用**实验矩阵**定位(采集开/关 × 不同设备),比读驱动文档快
3. 嵌入式里"能用"和"并发时能用"是两回事——单独测都好的组件,合起来才暴露约束

## Bug 6:配置键落错 section,改配置无效

**现象**:用户把 `asr_segment_timeout_ms` 改成 1000,行为没变化。

**定位**:cat 板端 config.ini 发现该键躺在 `[chat]` 节里(追加配置时位置错了)。解析器在 [chat] 分支找不到这个键 → **静默忽略**。

**根因**:手写 ini 解析器对未知键静默;追加键时没核对 section 归属。

**修复**:把键移到 [asr] 节;同时程序侧把唤醒词自动并入关键词表,减少"用户要改两处"的机会。

**思维教训**:静默忽略是一把双刃剑——健壮(拼错不崩)但隐蔽(改错没反应)。对策:**启动日志打印实际生效的关键配置**(项目里的 `[Config] 主码流:...` 就是干这个的),排查时先看"程序眼里的配置是什么"。

## Bug 7:回声——TTS 播放时 mic 录到自己的声音

**现象**:对话功能上线后,播放 LLM 回复时,喇叭声被 mic 录进去,ASR 把"自己的话"识别成用户新输入(严重的会自问自答循环)。

**定位**:播放期间 ASR 的识别文本 = 喇叭内容的转写,证据充分。

**修复**:三重防线:
1. **token 级门控**:播放期间 ASR 直接丢弃 token(不只是丢段落——关键词匹配在 token 层!)
2. **尾 2s 继续丢**:ASR 攒帧+推理有 ~1.5s 延迟,播放停止后解出的仍是回声
3. 静音门控辅助(回声音量低时根本不推理)

**思维教训**:分析系统里的"反馈回路"——mic 和喇叭同处一个空间,输出会变成输入。门控窗口必须**覆盖全链路的延迟**,只算播放时长一定漏。

---

## Bug 8:静音门控吃掉每句话的开头

**现象**:语音识别"断断续续"——用户说短句(2 秒内)几乎全部丢失,说长句才正常。

**定位**:观察日志的时间戳规律:每句话只蹦出零星字。审查静音门控:

```cpp
// 旧逻辑:silent_ 为真时直接丢弃 PCM 不喂 fbank
if (cfg_.silence_gate && silence_probe_ && silence_probe_()) continue;
```

而 `silent_` 每秒才更新一次——**开口的瞬间它还是"静音"状态**,头 1~2 秒数据被丢;短句总共才 2 秒,几乎全灭。

**根因**:控制信号的更新频率(1s)远慢于被控事件(说话开始是毫秒级的)。

**修复**:静音时**照喂数据**(语音开头完整进 fbank),只是**不推理**(省 NPU);连续静音 2s 才重建丢弃积压。双条件防抖:距上次出词 2s 内绝不重建。

**思维教训**:门控/丢弃类逻辑,先问"控制信号的滞后是多少,被滞后吃掉的部分能不能承受"。不能承受 → 改"延迟丢弃"(先收着,确认不需要了再丢),而不是"即时丢弃"。

---

## 八个 bug 的模式总结(记这四条就够)

| 模式 | Bug 编号 |
|---|---|
| **生命周期颠倒**:谁在用谁,谁先停 | 1、2 |
| **语义漂移**:函数/配置/机制的含义与使用方理解不一致 | 3、4、6 |
| **并发与硬件约束**:单独好用,合起来冲突 | 5 |
| **反馈回路与时序**:输出变输入、控制信号滞后 | 7、8 |

最后一条学习建议:把每个 bug 的"定位过程"重走一遍,重点不是"当时怎么修的",而是**"线索是怎么一步步指向根因的"**——定位方法比修复方法通用得多。
