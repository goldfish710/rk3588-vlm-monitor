## 4.1 std::atomic:单变量跨线程共享的轻量方案

### 为什么不能直接用 bool

```cpp
bool running = true;      // 线程 A 写,线程 B 读
// C/C++ 标准里这是"未定义行为":编译器可能把读优化成只读一次(缓存),
// CPU 可能乱序,线程 B 可能永远看不到 false。
```

### std::atomic:保证"一个变量的读写跨线程可见"

```cpp
std::atomic<bool> running{true};
running.store(false);          // 写
bool r = running.load();       // 读——保证看到最新值
```

**什么时候用 atomic、什么时候用锁?**
- 单个 bool/int 的"状态标志" → atomic(轻量,无上下文切换)
- 多个变量一起修改/复杂数据结构 → mutex(锁保护整体一致性)

### 项目实例:全项目的停止标志

```cpp
// server/TLServer/TLmain.cpp 等
std::atomic<bool> exit_flag(false);     // 全局退出标志
std::atomic<bool> g_h265_thread_alive;  // 编码线程存活标志
// AsrEngine 里:
std::atomic<bool> suppress_input_{false};   // 回声门控(ASR 线程读,Chat 线程写)
```

suppress_input_ 特别典型:ChatEngine 播放 TTS 时置 true,ASR 线程每 token 检查——**跨模块的"状态通知"用 atomic,一纳秒开销**:

```cpp
// server/cpp/asr_thread.cpp  onToken()
if (suppress_input_.load()) return;   // 播放期间丢弃回声 token
```

如果这里用 mutex,每个 token(每秒 5~10 次)都要加解锁——浪费。

## 4.2 生产者-消费者模式:项目的主旋律

项目里几乎每对线程都是这个模式:

```
生产者线程               队列(锁+条件变量)            消费者线程
编码线程 ──→ SharedQueue ──→ RTSP 直播源
采集线程 ──→ PCM 队列   ──→ ASR 线程
采集线程 ──→ 音频帧 ────→ AAC 编码(内联,见下)
ASR 线程 ──→ 事件队列  ──→ ChatEngine 线程
ChatEngine ──→ MQTT 队列 ──→ MQTT 线程
```

### 通用骨架(把项目里所有队列抽象出来)

```cpp
template <typename T>
class SafeQueue {
    std::deque<T> q_;
    std::mutex m_;
    std::condition_variable cv_;
    size_t max_;                              // 有界:防内存爆

public:
    void push(T v) {
        {
            std::lock_guard<std::mutex> lk(m_);
            if (q_.size() >= max_) q_.pop_front();   // 满则丢最旧(实时系统策略!)
            q_.push_back(std::move(v));              // 移动零拷贝
        }
        cv_.notify_one();
    }
    bool pop(T &out) {                       // 非阻塞取(SharedQueue 风格)
        std::lock_guard<std::mutex> lk(m_);
        if (q_.empty()) return false;
        out = std::move(q_.front());
        q_.pop_front();
        return true;
    }
    bool wait_pop(T &out, int timeout_ms);   // 阻塞取(ASR 风格,超时+谓词)
};
```

项目里的 SharedQueue、AsrEngine 队列、ChatEngine 事件队列、MQTT 队列,全是这个骨架的变体。

### 为什么"满则丢最旧"

这是**实时系统的经典策略**:视频流/音频流如果消费者慢,宁可丢帧也不能无限堆积(否则内存爆+延迟越来越大)。丢掉的是"最旧"的数据(已经过时的画面),保留最新的。所以你的 VLC 偶尔卡一下但很快恢复——丢帧保实时。

## 4.3 线程优先级:nice 值让谁先跑

### 项目实例:两级优先级体系

```cpp
// server/TLServer/EncodeThread.cpp  视频/AI 线程:最高优先级(负数=更优先)
setpriority(PRIO_PROCESS, (pid_t)syscall(SYS_gettid), -5);

// server/TLServer/AudioCapture.cpp  音频采集:低优先级,让视频
setpriority(PRIO_PROCESS, (pid_t)syscall(SYS_gettid), 10);

// server/cpp/asr_thread.cpp  ASR 线程:同样低优先级
setpriority(PRIO_PROCESS, (pid_t)syscall(SYS_gettid), 10);
```

设计思想:
- 视频编码/AI 是**实时链路**:30fps 每帧 33ms 的硬期限,必须优先
- 音频/ASR/对话是**软实时**:丢 100ms 音频无感,晚 0.5s 识别无感
- nice 值从 -20(最优先)到 19(最不优先);视频 -5、音频 10,让出近一半调度权重

还有两个配套动作:

```cpp
pthread_setname_np(pthread_self(), "h265_enc");   // 给线程起名
// top -H 或 /proc/<pid>/task/<tid>/comm 里能看到名字——调试利器
```

**为什么用 `(pid_t)syscall(SYS_gettid)` 而不是 getpid()**:getpid 返回进程 id,所有线程一样;gettid 返回线程 id——setpriority 必须作用在线程上。这是 Linux 细节,C 里 pthread 也有同样的坑。

## 4.4 项目实例:ASR 线程的完整生命周期(综合练习)

把第 3、4 章全部知识串一遍,读这段:

```cpp
// server/cpp/asr_thread.cpp
void AsrEngine::start() {
    if (running_.load()) return;
    running_ = true;                                    // atomic 标志
    thread_ = std::thread(&AsrEngine::asrLoop, this);   // 成员函数线程
}

void AsrEngine::asrLoop() {
    pthread_setname_np(pthread_self(), "asr_zip");
    setpriority(PRIO_PROCESS, (pid_t)syscall(SYS_gettid), 10);   // 低优先级

    while (running_.load()) {                           // ① 停止标志
        PcmChunk chunk;
        {
            std::unique_lock<std::mutex> lock(q_mtx_);
            q_cv_.wait_for(lock, std::chrono::milliseconds(200), [this] {
                return !queue_.empty() || !running_.load();
            });                                          // ② 等数据或退出(带超时)
            if (queue_.empty()) {
                if (!running_.load()) break;
                // 顺便执行周期任务:段落超时落盘
                if (!cur_segment_.empty() && now_ms() - last_token_ms_ > cfg_.segment_timeout_ms)
                    flushSegment();
                continue;
            }
            chunk = std::move(queue_.front());           // ③ 移动取数据
            queue_.pop_front();
        }
        // ... 重采样 → fbank → chunk 推理(几百 ms,都在锁外!)
    }
}
```

**逐条检查设计**:
1. 重活(推理几百 ms)**全部在锁外**——锁内只做队列操作,这是锁粒度的黄金法则
2. 条件变量的超时被复用为"定时器":每 200ms 检查一次段落超时,不额外开线程
3. 移动语义:音频数据从队列搬到局部,零拷贝
4. 停止路径:running_ 置 false → notify → 谓词为真醒来 → break

## 4.5 项目实例:回调跨线程的纪律(再看一次,更深刻)

```cpp
// TLmain 接线:回调在 ASR 线程执行
asr_engine->setSegmentCallback([chat_engine](const std::string &seg) {
    chat_engine->onSegment(seg);     // 内部只做一件事:入队!
});

// chat_engine.cpp
void ChatEngine::onSegment(const std::string &segment) {
    std::lock_guard<std::mutex> lock(ev_mtx_);     // 锁队列
    ev_queue_.push_back({EV_SEGMENT, segment, 0.0f});
    ev_cv_.notify_one();                            // 通知对话线程
}
```

为什么必须这样?如果 onSegment 里直接调 DeepSeek API(网络 1 秒+),ASR 线程就卡 1 秒,这 1 秒的音频没人识别,之后全乱。**回调纪律:回调里只入队,把活交给属于它的线程**——这就是"每个模块一个线程+队列"架构的由来。

## 一句话总结

单变量状态 → atomic;复杂数据 → 锁;线程间传数据 → 有界队列(满丢最旧);回调跨线程 → 只入队。这四句话能解释项目 90% 的线程代码。
