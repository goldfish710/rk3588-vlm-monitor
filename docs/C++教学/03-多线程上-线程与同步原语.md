## 3.1 std::thread:C 的 pthread 换皮

### C 的做法

```c
#include <pthread.h>
void* worker(void* arg) { ... return NULL; }
pthread_t t;
pthread_create(&t, NULL, worker, &data);   // 传参数要 void* 强转
pthread_join(t, NULL);                     // 忘记 join 会泄漏线程资源
```

### C++ 的 std::thread

```cpp
#include <thread>
void worker(int a) { ... }
std::thread t(worker, 10);        // 直接传参数,自动类型检查
t.join();                         // 等它结束
```

### 项目实例:成员函数线程

```cpp
// server/cpp/asr_thread.h
std::thread thread_;
void start() {
    running_ = true;
    thread_ = std::thread(&AsrEngine::asrLoop, this);   // 成员函数 + this
}
```

`&AsrEngine::asrLoop` 是成员函数指针,第一个参数必须是对象指针 `this`——等价于 pthread 的 `pthread_create(&t, NULL, wrapper, this)`,但类型安全。

## 3.2 数据竞争:两个线程同时改一个变量会怎样

```cpp
// 共享变量 count,两个线程各加 10000 次:
int count = 0;
void add() { for (int i = 0; i < 10000; i++) count++; }
// 结果不是 20000!因为 count++ 是三步:读→加→写,
// 线程 A 读到 5 时,线程 B 也读到 5,各写回 6 → 丢了一次加。
```

这叫**数据竞争(race condition)**,C 里同样存在,但 C 教程很少讲——多线程 C 项目本来就少。你的项目里线程比一般项目多,所以同步是头等大事。

### 解法一:std::mutex + std::lock_guard

```cpp
#include <mutex>
std::mutex m;
int count = 0;
void add() {
    for (int i = 0; i < 10000; i++) {
        std::lock_guard<std::mutex> lock(m);   // 构造:加锁
        count++;                                // 临界区
    }                                           // 离开作用域:自动解锁(RAII!)
}
```

**lock_guard 是 RAII 版加锁**:C 里 `pthread_mutex_lock` 之后任何提前 return 都会忘记 unlock;lock_guard 把解锁交给析构,不可能忘。

### 项目实例:SharedQueue(最小线程安全队列)

```cpp
// server/TLServer/SharedQueue.cpp
bool SharedQueue::push_packet(const H265EncodePacket &packet)
{
    std::lock_guard<std::mutex> lock(mutex_);     // 进临界区
    if (queue_.size() >= max_size_)
        queue_.pop_front();                        // 满则丢最旧帧
    queue_.push_back(packet);
    return true;
}                                                  // 出临界区,自动解锁

bool SharedQueue::pop_packet(H265EncodePacket &packet)
{
    std::lock_guard<std::mutex> lock(mutex_);
    if (queue_.size() == 0) return false;
    packet = queue_.front();
    queue_.pop_front();
    return true;
}
```

编码线程往队列塞编码帧,RTSP 线程取帧发流——两个线程永远不同时碰 queue_ 内部结构。

**关键认知**:锁保护的是**数据结构(queue_ 的内部状态)**,不是业务逻辑。凡是多个线程能碰到的容器,每次访问都要在锁内。

## 3.3 条件变量:别忙等,有事再叫我

### 忙等的愚蠢

```cpp
// 消费者:队列没数据就一直转圈查(烧 CPU,项目里绝不能这么写)
while (queue.empty()) { /* 空转 */ }
```

### 条件变量的"等-通知"模型

```cpp
std::mutex m;
std::condition_variable cv;
std::deque<int> q;

// 消费者:
std::unique_lock<std::mutex> lock(m);
cv.wait(lock, [] { return !q.empty(); });   // 睡着,直到谓词为真
// ← 醒来时锁已自动重新持有,q 必非空
int v = q.front(); q.pop_front();

// 生产者:
{
    std::lock_guard<std::mutex> lock(m);
    q.push_back(v);
}
cv.notify_one();     // 叫醒一个睡着的消费者
```

三个要点:
1. wait 必须传**谓词**(lambda)——这是防"虚假唤醒"和"丢失唤醒"的标准写法
2. wait 内部:解锁→睡觉→被叫醒→**重新加锁**→检查谓词(为假继续睡)
3. notify 最好在锁外调用(锁内也行,只是被叫醒的线程要先等锁,略慢)

### 项目实例:AsrEngine 的 PCM 队列(完整模式)

```cpp
// server/cpp/asr_thread.cpp  asrLoop()
std::unique_lock<std::mutex> lock(q_mtx_);
q_cv_.wait_for(lock, std::chrono::milliseconds(200), [this] {
    return !queue_.empty() || !running_.load();    // 有数据 或 要退出
});
if (queue_.empty()) {
    if (!running_.load()) break;
    continue;          // 200ms 超时但没退出:继续等(顺便做超时检查)
}
```

两个精妙点:
1. **wait_for 带超时**:纯 wait 会睡死。这里 200ms 醒一次,顺便检查"段落超时"等周期性任务——**一个条件变量同时服务"等数据"和"定时任务"**
2. 谓词里带 `!running_`:**停止时 notify_all 后线程能干净退出**(第 12 章会讲为什么这很重要)

```cpp
// 生产者侧(采集线程调用的 feedPcm):
{
    std::lock_guard<std::mutex> lock(q_mtx_);
    if (queue_.size() >= kQueueMax) queue_.pop_front();   // 有界:丢最旧
    queue_.push_back(std::move(mono));
}
q_cv_.notify_one();   // 锁外通知
```

## 3.4 项目实例:AudioCapture 的停止机制(优雅停线程)

线程怎么停?三个要素,缺一不可:

```cpp
// server/TLServer/AudioCapture.h
std::atomic<bool> running_{true};      // ① 停止标志(原子,见第 4 章)

// server/TLServer/AudioCapture.cpp  shutdown():
running_ = false;                      // ② 置标志
if (pcm_) snd_pcm_drop(pcm_);          // ③ 打断阻塞的系统调用!
if (thread_.joinable()) thread_.join(); // ④ 等线程真正结束

// captureLoop() 里的配合:
while (running_.load()) {              // 每轮检查标志
    snd_pcm_sframes_t n = snd_pcm_readi(...);   // 阻塞读
    if (n < 0) {
        if (!running_.load()) break;   // 被 drop 打断 → 退出
        ...
    }
}
```

**教训**(我们项目踩过的):光置标志没用——如果线程阻塞在 `readi` 上,它永远看不到标志。必须**打断阻塞调用**(snd_pcm_drop),让 readi 返回,线程才有机会检查标志。这个"停线程三部曲"在任何有阻塞 IO 的线程里都要做。

## 3.5 项目实例:ChatEngine 的 stop(更细的退出顺序)

```cpp
// server/cpp/chat_engine.cpp
void ChatEngine::stop() {
    if (!running_.load()) return;
    running_ = false;             // ① 置标志
    ev_cv_.notify_all();          // ② 叫醒所有等在条件变量上的循环
    if (thread_.joinable()) thread_.join();   // ③ join 等退出
    if (play_state_cb_) play_state_cb_(false);  // ④ 收尾:解除回声门控
}
```

和 AudioCapture 对比:AudioCapture 打断阻塞靠 snd_pcm_drop,ChatEngine 打断"等事件"靠 notify_all。**不同阻塞方式对应不同打断手段**,这就是看代码时要问的第一问题:"这个线程会阻塞在哪?怎么被打断?"

## 一句话总结

线程=独立的执行流;锁=保护数据结构;条件变量=高效地等事件。看任何线程代码先问三个问题:共享了哪些数据?怎么保护的?阻塞在哪、怎么被叫醒/打断?
