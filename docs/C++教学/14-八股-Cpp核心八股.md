# 14-八股:C++ 核心八股(项目实例版)

> 每题格式:【结论】→【原理】→【项目实例】。所有实例都是本项目真实代码/真实踩坑,
> 面试被追问能一路讲到修复过程。基础语法类从简,并发/内存/现代 C++ 是重点。

## 一、基础语法

### Q1 指针和引用的区别?
**结论**:引用是别名(定义必须初始化、不可重绑定、无空引用),指针是地址变量
(可空、可改指)。语法上引用无解引用符号;底层实现引用就是指针(汇编层面一致)。
**项目实例**:函数传大对象用 const 引用(`const MainStreamConfig& ms`);回调用
std::function 值传递。

### Q2 const 的各种位置?
**结论**:`const int *p` 指向常量(不能改 *p);`int * const p` 指针常量(不能改 p);
`const int * const p` 都不能改;成员函数后 `const`(如 `getPersons() const`)
表示该函数不修改成员、可被 const 对象调用。
**项目实例**:PersonTracker::getPersons() const + mutable mutex 的经典组合——
逻辑 const 与物理 const 的差异,mutex 用 mutable 修饰才能在 const 函数里加锁。

### Q3 static 的三种用法?
**结论**:①局部 static:生命周期全程、首次执行时初始化(C++11 起线程安全);
②类 static 成员:所有对象共享一份;③全局 static:限制符号仅本文件可见(内部链接)。
**项目实例**:`mpp_alloc_cma_fd` 里 `static int heap_fd` 缓存打开的 fd 只开一次;
匿名 namespace 的函数 = 内部链接,等价全局 static。

### Q4 C++ 内存分区?
**结论**:栈(函数局部变量,自动管理)、堆(new/malloc,手动管理)、全局/静态区、
代码区(只读)。栈溢出=递归过深/局部大数组;堆溢出=越界写。

## 二、编译链接与内存管理

### Q5 new/delete 和 malloc/free 的区别?
**结论**:new 是运算符:分配内存 + **调用构造函数**,失败抛异常;malloc 是函数:
只分配内存、返回 void*、失败返回 NULL。配套:new[]/delete[] 成对;
free 不需要类型转换。**项目实例**:cJSON 等 C 库接口混用时注意 malloc 的内存
要 free 而不是 delete(跨语言边界的内存管理约定)。

### Q6 内存泄漏怎么排查?
**结论**:症状=RSS 只涨不降。手段:①RSS 曲线观察(本项目板端做法)②工具
(valgrind/ASAN,板端常跑不动)③代码审计生命周期。
**项目实例**:流式 ASR fbank 特征缓存泄漏——每帧特征累积不清,板端 RSS 缓慢上涨;
定位:RSS 曲线 + 审计 fbank 对象生命周期;修复:状态清理函数重建 fbank 并归零计数。
教训:**泄漏不一定崩,先看"涨不涨"**。

### Q7 野指针/悬空指针?
**结论**:野指针=未初始化;悬空指针=指向已释放内存。使用后果未定义。
**项目实例**:VLM 流式回调 `on_delta_` 是跨轮复用的成员函数对象,run 返回后
立即置空——防上一轮增量转发到下一轮(回调生命周期显式管理,用完即清)。

### Q8 RAII 是什么?项目里怎么用的?
**结论**:Resource Acquisition Is Initialization——资源获取即初始化,把资源的
生命周期绑定到对象上,构造获取、析构释放。异常/提前返回路径也保证释放。
**项目实例**:Mppclass 析构里 mpp_buffer_put→cfg deinit→mpp_destroy 全链释放;
PlaybackSession open/finish 成对;线程也按 RAII 思维管理(ChatEngine::stop 顺序:
置标志→唤醒 cv→join→释放 VLM)。退出日志里每行"资源释放完成"都是 RAII 的证明。

## 三、面向对象

### Q9 多态的实现原理?虚函数表?
**结论**:有虚函数的类有一张虚表(vtable,存虚函数地址),对象里一个 vptr 指向它;
调用虚函数 = 通过 vptr 查表跳转(间接调用,略慢于直接调用)。纯虚函数=接口。
**项目实例**:`TtsBackend` 抽象基类(synth 纯虚)+ 两个实现(云端火山/本地 Piper),
工厂按配置实例化——换后端零改动。多态代价的思考:虚函数开销在音频路径可忽略;
VLM/ASR 只有一个实现就没做抽象层(拒绝过度设计)。

### Q10 为什么析构函数要虚?
**结论**:基类指针 delete 派生类对象时,基类析构非虚 → 只调基类析构,派生类资源
泄漏;虚析构保证按派生→基类顺序完整析构。
**项目实例**:TtsBackend 的析构就是 virtual(接口类的标配);纯数据类
(如 MQTTEvent)不需要虚析构——虚析构只在"会被多态 delete"时必要。

### Q11 构造和析构的顺序?
**结论**:构造:基类→成员(声明顺序)→自身函数体;析构严格相反。多继承按声明顺序。

## 四、C++11/14/17 现代特性

### Q12 右值引用和 move 语义?项目里怎么用的?
**结论**:右值=临时对象(即将销毁),右值引用 `T&&` 可以"偷"它的资源;
std::move 只是类型转换(转成右值引用),真正的资源转移发生在移动构造/赋值里;
move 后原对象处于"有效但未定义"状态,不应再使用。
**项目实例**:TTS 句队列 `sent_q_.push_back(std::move(s))`——一句 PCM 几万到
几十万样本(几百 KB),move 只转移指针零深拷贝;双队列流水线每个数据只被消费
一次,"独占所有权"是 move 的前提,天然满足。

### Q13 lambda 的捕获方式?项目里怎么用的?
**结论**:[] 不捕获;[=] 值捕获;[&] 引用捕获;[this] 捕获 this 指针;
[=, &x] 混合。捕获引用要保证生命周期(捕获 this 时对象必须活着)。
**项目实例**:ASR 回调 `setSegmentCallback([chat_engine](seg, ts){ ... })` 按值捕获
指针(生命周期由 TLmain 保证);VLM 流式回调 `[this](delta){ onVlmDelta(delta); }`
捕获 this——run 期间 chat 线程同步调用,生命周期安全(红线设计:VLM 只在本线程)。

### Q14 auto 和 nullptr?
**结论**:auto 编译期类型推导(不影响运行效率);nullptr 是 `std::nullptr_t` 类型,
能区分重载,替代 NULL(本质是 0,有 int/指针二义性陷阱)。
**项目实例**:项目里迭代器/复杂类型用 auto 提高可读性(如 `for (auto& c : cands)`)。

## 五、智能指针

### Q15 unique_ptr/shared_ptr/weak_ptr 各自场景?项目实例?
**结论**:
- unique_ptr:独占所有权,零开销(大小=裸指针)
- shared_ptr:共享所有权,引用计数;跨线程传递安全(计数原子)
- weak_ptr:不占所有权的观察者,解决 shared_ptr 循环引用
**项目实例**:`unique_ptr<TtsBackend> tts_`(独占后端实例);
`shared_ptr<std::promise<FallConfirmResult>>`(复核任务入队后,promise 同时被
队列和等待方持有——谁先销毁都不悬空);跨线程传对象的原则:传值不传裸指针。

### Q16 shared_ptr 循环引用?weak_ptr 怎么破?
**结论**:A 持有 B 的 shared_ptr、B 持有 A 的 shared_ptr → 引用计数永不为 0 泄漏;
一方改持 weak_ptr 打破环。
**项目实例**:本项目队列/回调设计刻意避免了"对象间互相 shared_ptr"——数据流
是单向的(生产者→队列→消费者),天然无环,所以没用到 weak_ptr(能讲出"为什么
不需要"也是加分)。

## 六、并发(项目重头戏,必背)

### Q17 mutex 和 condition_variable 怎么配合?四要素?
**结论**:互斥锁保护**数据结构**,条件变量通知**状态变化**。标准模式四要素:
①锁(unique_lock + mutex)②谓词(wait 的第二个参数,防虚假唤醒)③通知
(notify_one/all)④**通知与谓词变更同侧**(谁改了状态谁发通知)。
**项目实例**:项目 10+ 线程、4 对生产者-消费者队列全部这套模式(采集→AI 帧队列、
ASR→chat 事件队列、chat→synth 句队列、synth→play 波形队列)。

### Q18 虚假唤醒和丢失唤醒?
**结论**:虚假唤醒=条件变量可能"无缘无故"返回,所以 wait 必须带谓词重查;
丢失唤醒=通知发生在等待开始之前 → wait 错过。标准模式(谓词+锁)天然防两者。
**项目实例(两个真实死锁 bug,必背)**:
1. **消费者不通知生产者**:播放线程从波形队列 pop 后忘了 notify——合成线程在
   "队列满"背压等待里等空位,而空位是消费者 pop 出来的 → 永久冻结。现象:长回答
   播到第 8 句后卡死,按退出才放出余句。修复:pop 后补 notify_one,两行代码。
2. **标志漏置**:合成线程"本轮全部句已合成"分支漏置 synth_done_ → 播放线程
   等"本轮完成"的通知永远不来 → 回声门控不解除 → 麦克风采集永久暂停。现象:
   第一次对话正常,之后 asr_text.txt 一个字没有。修复:补一行标志位+通知。

### Q19 lock_guard 和 unique_lock 的区别?
**结论**:lock_guard 构造加锁、析构解锁,不可手动控制;unique_lock 更灵活
(可 defer lock、可提前 unlock、可被条件变量 wait 使用——wait 会临时释放锁)。
**项目实例**:普通临界区用 lock_guard;所有 cv.wait 必须用 unique_lock。

### Q20 atomic 和 mutex 怎么选?
**结论**:atomic=无锁的单个变量原子读写(CAS 实现),适合标志位/计数器,
无上下文切换开销;mutex=保护**复合操作**(多个变量的不变式)。原子只保证
单个操作的原子性,不保证整体逻辑。
**项目实例**:`running_`/`preempt_voice_`/`urgent_count_` 等标志用 atomic;
队列+条件变量用 mutex——"标志位用原子,数据结构用锁"。

### Q21 死锁的四个必要条件?项目怎么踩的?
**结论**:①互斥(资源独占)②持有并等待③不可剥夺④循环等待——四者缺一不死锁。
破法:统一加锁顺序、try_lock、超时。
**项目实例**:见 Q18 两个 bug(严格说是"活锁式冻结"而非经典互锁死锁——面试能
区分"死锁"与"条件变量通知缺失导致的永久等待"是加分项,后者是我项目真实踩的)。

### Q22 thread 的 join/detach?线程退出安全?
**结论**:join=主线程等子线程结束(回收资源);detach=分离后台运行(进程结束时
资源由系统回收,但析构期访问其资源不安全)。**推荐 join + 退出标志**模式。
**项目实例**:所有线程都是"运行标志 + 循环检查点 + join"模式;退出顺序有讲究:
先打断 rkllm_run(abort),否则 join 要等完整生成(实测多等 8s+)——join 前
必须先唤醒所有阻塞点(标志+notify_all 双保险)。

### Q23 future/promise 怎么用?项目实例?
**结论**:promise=结果的生产端(set_value 写入),future=结果的消费端(get/wait
读取),是"一次写入、一次读取"的跨线程结果通道。
**项目实例(跌倒复核链)**:事件线程 requestFallConfirm → 创建 promise 拿 future →
任务入 urgent 队列;chat 线程(唯一能碰 VLM 的线程)执行复核 → set_value;
事件线程 `future.wait_for(12s/30s)` 拿结果,超时按"无法确认"兜底直报——
future/promise 让"请求方任意线程、执行方单线程"解耦,超时是报警链路的兜底保险。

## 七、性能与工程

### Q24 零拷贝是什么?项目三层怎么讲?
**结论**:零拷贝=零 **CPU 拷贝**,数据通过 DMA/页表在硬件模块间流转,CPU 不参与。
不是"数据不动"(物理上不可能),是"CPU 不搬"。
**项目三层**(对应三种机制):①V4L2 DMABUF:编码器分配缓冲导出 fd,ISP 通过 DMA
直接写进编码器缓冲;②mmap:CPU 必须碰数据的环节(画框)把 CMA 缓冲映射进地址空间
原地写;③RGA:专用硬件引擎做"搬+转"一趟活(旋转/格式转换顺带完成)。
**量化**:A/B 实测插 3 次全帧拷贝,编码延迟 10.8→17.9ms(+66%)。
**反面教材**:带缓存的 mmap 引发 CPU/DMA 数据不一致(框拖影)——dma_buf_sync
括号解决。零拷贝不等于零问题。

### Q25 缓存一致性是什么?项目踩的坑?
**结论**:CPU 写内存先进 cache,DMA 设备直接读写 DRAM——两边看到的数据不同步。
嵌入式无 IOMMU 时这是高频坑。解法:dma-buf 生态的 DMA_BUF_IOCTL_SYNC
(CPU 读前 START|READ 失效、写后 END|WRITE 刷出),括号必须完整且无条件每帧执行。
**项目实例**:画框拖影——只在"干净帧快照"路径做了 START,画框路径没做 → 拖影
复发;修复为画框前无条件每帧失效。

### Q26 为什么跨线程不传裸指针?
**结论**:生命周期不可控(谁负责释放?对方线程还活着吗?),并发读写还要加锁。
**项目实例**:ASR→chat 回调只传 std::string 拷贝,chat→事件线程只传值;
必须共享的对象用智能指针(future/promise 模式)或明确所有权(unique_ptr)。
原则:**传值传所有权,共享先谈生命周期**。

## 附:项目真实修过的并发/内存 bug 速记(面试故事弹药库)

2. synth_done_ 标志漏置 → 首轮对话后 ASR 永久失活(补标志位+通知)
3. fbank 特征缓存泄漏 → RSS 缓慢上涨(清理函数重建 fbank)
4. UTF-8 按字节截断孤立引导字节 → 输出乱码(回退到字符边界)
